No FFmpeg CLI, external codec library, GPL, version3 or nonfree feature was requested. Built-in codecs are still compiled: four library features do **not** imply a four-codec build. This is not a final capability/license/security selection. The source's existing chapter-timebase and subtitle callback quirks are likewise retained, not repaired by a dependency recipe.

## Smallest meaningful proof

`probe.cpp` creates an original three-frame 16×16 grayscale FFV1 Matroska file through the newly built FFmpeg libraries. It writes known per-pixel values and stream title/language, calls the private `FFMS_GetTrackName` and `FFMS_GetTrackLanguage` APIs, indexes normally, and requests frames in order 2, 0, 1 with `FFMS_SEEK_NORMAL`. Every decoded pixel and the indexed frame count must match; public-header and runtime FFMS version must both be 5.1.0. Metadata pointers are consumed before indexing destroys the indexer.

This is a narrowly scoped executable/CTest observation, not the application's test suite. Success would establish normal indexing/frame retrieval and nonempty private metadata calls from a matched recipe, not chapters, subtitle callback units, attachments, compressed long-GOP/VFR accuracy, cancellation or all private behavior. Because fixture generation directly links FFmpeg too, its success cannot independently prove the exported FFMS2 target's transitive static link closure; a later FFMS-only consumer must check that seam. AviSynth/VapourSynth plugin entry points are outside this minimal target, not approved product exclusions. Existing private-API quirks are not corrected.

## Tools, resource boundary and proposed next execution

The library slice needs Git, CMake ≥3.28, Ninja, a C++17 compiler, the pinned compatible vcpkg executable/registry, and network/storage. The Windows triplet is release-only x64/static libraries/dynamic MSVC CRT; use the currently accepted latest MSVC in an initialized SDK environment and record its exact version. The Linux triplet is release-only x64/static libraries, intended for the platform agent's GitHub Actions runner; its exact GCC/glibc/image must be captured. These are prototype triplets, not qualified release targets.

The [source-derived dependency/download inventory](dependency-plan.json) contains the two target dependencies plus the owned port, six host ports, archive digests and HTTP HEAD observations. It is **not an executed vcpkg resolver result**. Target inputs are FFmpeg 7.1.2#5 and zlib 1.3.2#2; the host chain reaches `pkgconf` 3.0.3#1 and managed patched Meson 1.9.0#10 through `vcpkg-pkgconfig-get-modules`. The pinned tool catalog lists CMake 4.4.3, Ninja 1.13.2, Windows Python 3.14.7 and 7-Zip 26.03 candidates. Actual tool reuse/acquisition still needs resolution; the installed outer CMake 4.3.1-msvc1 does not establish that vcpkg will reuse it. [Pinned tool catalog](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/scripts/vcpkg-tools.json).

FFmpeg requests NASM on x64 and managed MSYS plus automake on Windows. Static traversal of the [pinned default MSYS recipe](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/scripts/cmake/vcpkg_acquire_msys.cmake) produces 29 packages, including the default 3.6.5 runtime. The [NASM 3.01 helper](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/scripts/cmake/vcpkg_find_acquire_program%28NASM%29.cmake) supplies download URLs only on Windows. NASM was absent in the separate Linux preflight; that system prerequisite needs explicit provisioning before this graph can build there. Missing Meson on PATH is different: the pinned host port acquires its own patched source. These upstream recipe tools are separate from project bootstrap scripts.

On 2026-09-27, 37 of 38 Windows candidates advertised sizes totalling **101,289,596 bytes (96.6 MiB)**; five of six Linux candidates advertised **71,751,626 bytes (68.4 MiB)**. These are partial remote-declared compressed-size sums, not complete transfer estimates or verified archive digests. FFmpeg did not advertise a size. The first MSYS mirror returned 404 for automake1.16 and MSYS zlib; all five recipe-listed fallback mirrors returned 200, and the sums use `repo.msys2.org` sizes for those two archives. Registry/history, FFMS2 Git transfer and possibly selected extraction support are additional unknowns. Linux may reuse more installed tools. No archive body was fetched for this inventory.

Exact cold acquisition, peak memory, scratch space and wall time remain **unmeasured**. The many built-in codecs make this larger than a header probe. Proposed initial operational ceilings are 2 GiB acquisition and 8 GiB scratch, two concurrent build jobs, stopping for review if exceeded; those are review bounds, not claimed requirements or enforced limits in these presets. `VCPKG_MAX_CONCURRENCY=2` is also needed for dependency builds; the CMake build preset limits only the small consumer.

The initial execution gate required manifest/tool resolution and root approval before full acquisition/build. That approval was subsequently granted for the bounded continuations below; this historical gate is not a new permission request. The existing VS vcpkg bundle stayed read-only. No Qt installer or SDK change was part of the Windows continuation; Linux prerequisites and dispatch have their own recorded authorization/evidence.

After the download/build gate is cleared and the separate pinned checkout/executable have been verified, set `HIKARI_PROTOTYPE_VCPKG_ROOT` to that checkout and `VCPKG_MAX_CONCURRENCY=2`, enter this folder and run:

```text
cmake --workflow --preset windows-overlay
cmake --workflow --preset linux-overlay
```

Run only the preset for that host. These workflows deliberately require an already provisioned, verified vcpkg toolchain; they are **not** Task48's complete pre-`project()` provisioner. The target package and consumer use `find_package(HikariFFMS2 CONFIG)`; no system-FFMS2 fallback exists. All generated state is under ignored scratch/build paths. The root owns later integration and GitHub workflow dispatch; `linux-ci/` remains the platform agent's separate scope.

## 2026-09-27 native results

Linux's [published run record](https://github.com/altqx/hikari/blob/8e93cc24d3a72befb55e439664ba7da68a69c94a/HikariSub/prototypes/build-workflow/ffms2-overlay/linux-ci/ci-run-notes.md) records a successful `linux-overlay` workflow at source `fd917555`, with the three-frame/private-metadata specimen. Its direct FFmpeg linkage does not independently prove the exported FFMS-only closure. The later Windows normalization change is not retroactively part of that Linux run.

Windows passed the combined specimen and a separately configured consumer that links **only** `HikariFFMS2::ffms2`. The latter indexed the authored input and decoded frame 0 with expected pixel 40, confirming the exercised static dependency closure on this Windows toolchain. [Windows report and exact invocation](evidence/windows-20260927/README.md), [machine-readable observations](evidence/windows-20260927/observations.json), [combined CTest output](evidence/windows-20260927/private-api-and-frames.txt), [FFMS-only link/runtime log](evidence/windows-20260927/ffms-only-build-and-run.txt).

The pinned registry and official tool identity have been verified in isolated scratch. Actual resolution exposed a feature-selection correction: the top-level manifest must explicitly list FFmpeg with `default-features: false`; setting it only on the owned port's dependency allowed avdevice/avfilter defaults. The corrected resolver chooses exactly the intended four library features plus core. Both [original](evidence/windows-20260927/resolution-original.txt) and [corrected scratch](evidence/windows-20260927/resolution-corrected-scratch.txt) plans are preserved. This agrees with [vcpkg's documented transitive-default behavior](https://learn.microsoft.com/en-us/vcpkg/users/versioning-troubleshooting#cause-unexpected-inclusion-of-default-features-in-transitive-dependencies); the source version pins did not change.

Acquisition/host probes are observations, not dependency qualification. The first vcpkg-triggered Git promisor fetch reported DNS failure; explicitly fetching the identical pinned port tree succeeded. The next checkout required `core.longpaths=true` in the owned scratch Git repository. The original deep build root then failed a compiler-check link with `LNK1104` for `intermediate.manifest`; [full diagnostic](evidence/windows-20260927/deep-path-compiler-failure.txt). The authorized retry uses `C:/Work/HikariF48` through supported buildtrees/packages/install/output path settings, retaining the old scratch and logs. No drive mapping or OS-wide setting changed.

Compiler/MSVC/SDK paths and versions are in [environment.json](evidence/windows-20260927/environment.json). Actual raw recipe hashes and their canonical Git comparisons, including CRLF differences, are in [recipe-identity-at-build.json](evidence/windows-20260927/recipe-identity-at-build.json). Managed CMake 4.4.3, 7-Zip/7zr 26.03 and the copied verified vcpkg tool have [captured hashes](evidence/windows-20260927/acquired-tool-sha256.json). The resolver acquired tools and ran compiler detection; `--dry-run` was not download/compiler-free.

The next strict source check exposed Git archive's Windows CRLF materialization. The port now restores LF **only** where that exact transformation matches the existing canonical digest, then verifies the written bytes strictly; all 20 inputs match. CMake required explicit `NEWLINE_STYLE LF`, since observed `file(WRITE)` used native CRLF. A [non-line-ending corruption specimen](evidence/windows-20260927/corruption-guard.json) was rejected without rewriting its input. No source/API behavior or lock digest changed.

Peak sampled combined scratch was **1,601,586,865 bytes**, conservative whole-host received delta **797,789,562 bytes**, and minimum sampled C: free **40,675,135,488 bytes**. No resource stop fired. Both roots counted toward the same allowance; the monitor used margins below the approved 2 GiB/8 GiB/25 GiB limits and the generated FFmpeg script used two jobs. These are sampled experiment observations, not calibrated throughput, exact package-only traffic or final installed-size budgets.

**Windows did not pass the unmodified deep-root `windows-overlay` workflow.** Success used its preset with explicit short buildtrees/packages/install/output routing, followed by build and CTest commands. No generated user preset, drive mapping, OS setting, Qt installer or production build was used.
