# FFMS2 owned overlay — source/recipe feasibility draft

**Throwaway slice for [Prove pinned CMake workflow provisioning on Windows and Linux](https://github.com/altqx/hikari/issues/48). No dependency build or runtime pass yet.** This folder proposes one source-matched FFMS2 library and a tiny native consumer. It does not provision Qt, implement a shipping helper, or replace the full accepted CMake workflow. The [backend contract](https://github.com/altqx/hikari/issues/62) selects isolated FFMS2 qualification first; this executable only proves the build dependency seam when actually run.

## Concrete inputs

[inputs.lock.json](inputs.lock.json) records the exact identities. vcpkg checkout/baseline `ee6a47dac031930715bea2e6dfb9ad60caaa5d83` requires tool release **2026-07-27** in its own [tool metadata](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/scripts/vcpkg-tool-metadata.txt). The already installed Windows executable matches that release's published SHA-256; the Linux digest is a declared release-asset identity, not a local Linux execution result. [Official release assets](https://github.com/microsoft/vcpkg-tool/releases/tag/2026-07-27).

The owned port takes [FFMS2 fork 45d5f721](https://github.com/altqx/ffms2/tree/45d5f72100d88c52acdd54bfedcc0315a44c735d) and [indexing_additional.cpp at parent 20d647c4](https://github.com/altqx/hikari/blob/20d647c4c769ab7f5d383cf3c1c33f03876a94e9/Thirdparty/Build/FFMS2/indexing_additional.cpp), Git blob `be378044fff07bac704f04dc57caa4fc5f95691e`. The extra file is digest-pinned; twenty relevant fork files have a checked SHA-256 manifest. It relocates only the extra file's two relative includes, retaining its MIT notice and behavior. The nine core translation units plus that file compile together against the same private/public headers. Installed consumers use that library's public headers and `FFMS_STATIC`; no distro or old bundled library is linked. [Existing provenance and mismatch warning](https://github.com/altqx/hikari/blob/20d647c4c769ab7f5d383cf3c1c33f03876a94e9/Thirdparty/PATCHES.md).

The fork's [configure requirements](https://github.com/altqx/ffms2/blob/45d5f72100d88c52acdd54bfedcc0315a44c735d/configure.ac#L91) establish the FFmpeg 6.1-era minimum: avformat 60.16, avcodec 60.31, avutil 58.29, swscale 7.5 and swresample 4.12. The hydrated local `Thirdparty/ffmpeg/README.txt` identifies Gyan 7.1.1, source `db69d06eee`; local headers report codec 61.19.101, format 61.7.100, util 59.39.100, swscale 8.3.100 and swresample 5.3.100. Those are local reference observations, not proof that an old binary was built from this recipe. This draft chooses vcpkg **FFmpeg 7.1.2#5**, port tree `bf414f1e4f2a63ff7410444dc4eabb5b392f6d16`, as a same-major compatibility candidate rather than inheriting registry-default 9.0.2. [Pinned version database](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/versions/f-/ffmpeg.json), [audited port tree](https://github.com/microsoft/vcpkg/tree/bf414f1e4f2a63ff7410444dc4eabb5b392f6d16).

The recipe's source archive has a fixed SHA-512. Feature defaults are disabled; only avcodec, avformat, swscale and swresample are requested (avutil is implicit). No FFmpeg CLI, external codec library, GPL, version3 or nonfree feature is requested. Built-in codecs are still compiled: four library features do **not** imply a four-codec build. This is not a final capability/license/security selection. The [official release page](https://ffmpeg.org/download.html) currently lists 7.1.5; shipping maintenance and later patch qualification remain separate. Source review suggests the selected API generation fits; compilation/link/runtime compatibility remains unproved.

One runtime qualification concern remains: the fork maps an audio option using [`out_channel_layout`](https://github.com/altqx/ffms2/blob/45d5f72100d88c52acdd54bfedcc0315a44c735d/src/core/audiosource.cpp#L35), while the hydrated 7.1 documentation names `out_chlayout`. Its [option helpers ignore get/set errors](https://github.com/altqx/ffms2/blob/45d5f72100d88c52acdd54bfedcc0315a44c735d/src/core/utils.h#L70). This is a source-level risk, not a demonstrated removed-option defect. The video-only probe cannot qualify audio resampling. The source's existing chapter-timebase and subtitle callback quirks are likewise retained, not repaired by a dependency recipe.

## Smallest meaningful proof

`probe.cpp` creates an original three-frame 16×16 grayscale FFV1 Matroska file through the newly built FFmpeg libraries. It writes known per-pixel values and stream title/language, calls the private `FFMS_GetTrackName` and `FFMS_GetTrackLanguage` APIs, indexes normally, and requests frames in order 2, 0, 1 with `FFMS_SEEK_NORMAL`. Every decoded pixel and the indexed frame count must match; public-header and runtime FFMS version must both be 5.1.0. Metadata pointers are consumed before indexing destroys the indexer.

This is a narrowly scoped executable/CTest observation, not the application's test suite. Success would establish normal indexing/frame retrieval and nonempty private metadata calls from a matched recipe, not chapters, subtitle callback units, attachments, compressed long-GOP/VFR accuracy, cancellation or all private behavior. Because fixture generation directly links FFmpeg too, its success cannot independently prove the exported FFMS2 target's transitive static link closure; a later FFMS-only consumer must check that seam. AviSynth/VapourSynth plugin entry points are outside this minimal target, not approved product exclusions. Existing private-API quirks are not corrected.

## Tools, resource boundary and proposed next execution

The library slice needs Git, CMake ≥3.28, Ninja, a C++17 compiler, the pinned compatible vcpkg executable/registry, and network/storage. The Windows triplet is release-only x64/static libraries/dynamic MSVC CRT; use the currently accepted latest MSVC in an initialized SDK environment and record its exact version. The Linux triplet is release-only x64/static libraries, intended for the platform agent's GitHub Actions runner; its exact GCC/glibc/image must be captured. These are prototype triplets, not qualified release targets.

The [source-derived dependency/download inventory](dependency-plan.json) contains the two target dependencies plus the owned port, six host ports, archive digests and HTTP HEAD observations. It is **not an executed vcpkg resolver result**. Target inputs are FFmpeg 7.1.2#5 and zlib 1.3.2#2; the host chain reaches `pkgconf` 3.0.3#1 and managed patched Meson 1.9.0#10 through `vcpkg-pkgconfig-get-modules`. The pinned tool catalog lists CMake 4.4.3, Ninja 1.13.2, Windows Python 3.14.7 and 7-Zip 26.03 candidates. Actual tool reuse/acquisition still needs resolution; the installed outer CMake 4.3.1-msvc1 does not establish that vcpkg will reuse it. [Pinned tool catalog](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/scripts/vcpkg-tools.json).

FFmpeg requests NASM on x64 and managed MSYS plus automake on Windows. Static traversal of the [pinned default MSYS recipe](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/scripts/cmake/vcpkg_acquire_msys.cmake) produces 29 packages, including the default 3.6.5 runtime. The [NASM 3.01 helper](https://github.com/microsoft/vcpkg/blob/ee6a47dac031930715bea2e6dfb9ad60caaa5d83/scripts/cmake/vcpkg_find_acquire_program%28NASM%29.cmake) supplies download URLs only on Windows. NASM was absent in the separate Linux preflight; that system prerequisite needs explicit provisioning before this graph can build there. Missing Meson on PATH is different: the pinned host port acquires its own patched source. These upstream recipe tools are separate from project bootstrap scripts.

On 2026-09-27, 37 of 38 Windows candidates advertised sizes totalling **101,289,596 bytes (96.6 MiB)**; five of six Linux candidates advertised **71,751,626 bytes (68.4 MiB)**. These are partial remote-declared compressed-size sums, not complete transfer estimates or verified archive digests. FFmpeg did not advertise a size. The first MSYS mirror returned 404 for automake1.16 and MSYS zlib; all five recipe-listed fallback mirrors returned 200, and the sums use `repo.msys2.org` sizes for those two archives. Registry/history, FFMS2 Git transfer and possibly selected extraction support are additional unknowns. Linux may reuse more installed tools. No archive body was fetched for this inventory.

Exact cold acquisition, peak memory, scratch space and wall time remain **unmeasured**. The many built-in codecs make this larger than a header probe. Proposed initial operational ceilings are 2 GiB acquisition and 8 GiB scratch, two concurrent build jobs, stopping for review if exceeded; those are review bounds, not claimed requirements or enforced limits in these presets. `VCPKG_MAX_CONCURRENCY=2` is also needed for dependency builds; the CMake build preset limits only the small consumer.

Before any full download/build: resolve the manifest with the pinned registry/tool, record target/host dependencies and required downloadable tool artifacts, then obtain root approval against that inventory. A dry-run may retrieve registry metadata, but must not be reported as a build. Keep the existing VS vcpkg bundle read-only; use an isolated ignored `_work/` checkout and cache. No Qt installer, SDK change, system package installation or CI dispatch is authorized by this draft.

After the download/build gate is cleared and the separate pinned checkout/executable have been verified, set `HIKARI_PROTOTYPE_VCPKG_ROOT` to that checkout and `VCPKG_MAX_CONCURRENCY=2`, enter this folder and run:

```text
cmake --workflow --preset windows-overlay
cmake --workflow --preset linux-overlay
```

Run only the preset for that host. These workflows deliberately require an already provisioned, verified vcpkg toolchain; they are **not** Task48's complete pre-`project()` provisioner. The target package and consumer use `find_package(HikariFFMS2 CONFIG)`; no system-FFMS2 fallback exists. All generated state is under ignored scratch/build paths. The root owns later integration and GitHub workflow dispatch; `linux-ci/` remains the platform agent's separate scope.

## Validation to date and remaining gates

Local source identities, exact private-file digest, official registry/version/port/tool metadata, source-derived dependency traversal and CMake preset parsing have been checked. HTTP HEAD queried candidate sizes without archive bodies. Only small recipe/metadata reads have occurred; no FFMS2/FFmpeg source payload, compiler invocation, dependency build or synthetic media execution has occurred for this overlay. No old prebuilt library is offered as proof.

Still required: actual resolver/tool/download trace; real Windows and Linux source builds; exported CMake target/static dependency closure; runtime source/library identity and three-frame result; cold/warm reconstruction and missing/corrupt input behavior; complete Qt/libass composition and loader/package/license manifests. The canonical accepted build contract and current Task48 record govern integration.
