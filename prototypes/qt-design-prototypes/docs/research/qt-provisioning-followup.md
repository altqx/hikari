# Qt 6.11.2: minimal official provisioning and artifact pinning

**2026-09-27; public source/metadata investigation for [Prove pinned CMake workflow provisioning on Windows and Linux](https://github.com/altqx/hikari/issues/48).** This follows the [prerequisite audit](../../HikariSub/prototypes/build-workflow/README.md). Under the authorized 20 MiB metadata-only bound, 27 official component metadata archives were downloaded, their publisher SHA-1 values verified, and their extracted scripts read as data. Total response bodies were below 1 MiB, including directory discovery. No installer or package script ran; no account file, terms acceptance, package change, SDK data payload or build was involved.

**Finding:** the inspected scripts contain no CLI-specific removal of the base documentation/example dependencies. However, the ID `qt.tools.qtcreator` now denotes **SDKTool**, not the full Creator IDE. Treating that ID as mandatory Creator GUI was incorrect. A fresh, explicitly selected SDK package set can plausibly omit the separate GUI package; a four-module-only installation without docs/examples is not established. The supported locking candidate is a frozen repository snapshot consumed by the official installer. This is a source-backed design, not a demonstrated installation or complete runtime-resolved closure.

## What flags and a full lock can do

`--no-force-installations` changes forced selection and `--no-default-installations` changes defaults. They do not remove hard dependencies. Official IFW 4.11.0 commit `aac2cf9c93b80a0f5959ab6c8a00bc378c54fdec` loads `Dependencies` separately from those overrides, and recursively resolves `currentDependencies()`. IFW also evaluates scripts and recalculates dependencies; XML inspection alone cannot replace that phase. [CLI options](https://doc.qt.io/qtinstallerframework/ifw-cli.html), [component loading](https://github.com/qtproject/installer-framework/blob/aac2cf9c93b80a0f5959ab6c8a00bc378c54fdec/src/libs/installer/component.cpp#L317), [dependency solver](https://github.com/qtproject/installer-framework/blob/aac2cf9c93b80a0f5959ab6c8a00bc378c54fdec/src/libs/installer/installercalculator.cpp#L192), [script/recalculation path](https://github.com/qtproject/installer-framework/blob/aac2cf9c93b80a0f5959ab6c8a00bc378c54fdec/src/libs/installer/packagemanagercore_p.cpp#L3445).

**Candidate A — CMake-verified frozen repository, preferred acquisition trace.** IFW supports `--set-temp-repository file:///…`. Proposed protocol:

1. Pin the official installer binary/version/hash and each enabled repository's XML, per-component or unified metadata, scripts/licenses, component revisions, archive filenames/URLs/lengths/SHA-256 and publisher sidecars. Metadata for unselected packages may still be fetched or supply shared functions. Include installer/controller configuration in the lock; a package version alone is insufficient.
2. Initial candidate closure: base architecture package plus multimedia and shader-tools leaves; SDKTool; base docs/examples; tools and license components; shared helper/patch metadata. Resolve conditional `mocwrapper`, Windows redistributables, add-on parents/docs/examples, and default/automatic nodes before declaring the final allowlist. Neither the full GUI nor debug packages should be silently added. The retained eight-archive Linux preflight is only the base payload list.
3. CMake fetches and verifies the complete allowed object set into isolated scratch, preserving official repository paths and metadata. Only then does the pinned official installer perform extraction, relocation and component operations against that local snapshot. Missing/changed objects fail before execution. Do not alter dependency entries to meet a size target.
4. Audit script-added repositories/downloads and restrict or observe data access. `--set-temp-repository` is not a network sandbox or authentication bypass. Compare resolved/installed components and accessed archives against the lock; verify required modules, tools and relocation. Cold/warm replay and missing/corrupt-input rejection remain unmeasured.

IFW's downloaded `.sha1` sidecars verify publisher-content agreement, but fetching a fresh sidecar from a mutable repository is not a committed Hikari SHA-256 lock. `--cache-path` denotes metadata caching, not a complete SDK payload mirror. [Repository/metadata format](https://doc.qt.io/qtinstallerframework/ifw-tools.html#repogen), [archive download/checksum logic](https://github.com/qtproject/installer-framework/blob/aac2cf9c93b80a0f5959ab6c8a00bc378c54fdec/src/libs/installer/downloadarchivesjob.cpp), [content verification](https://github.com/qtproject/installer-framework/blob/aac2cf9c93b80a0f5959ab6c8a00bc378c54fdec/src/libs/installer/downloadfiletask.cpp).

**Candidate B — official generated offline installer.** `create-offline` takes selected components plus the resolved dependency set and packages their data. Non-hybrid output removes repository configuration; hybrid output retains online maintenance. Lock the complete acquisition trace and resulting binary digest. This gives a replay artifact, not proof of an unaudited first capture, pruning, permitted redistribution or Qt-specific authentication behavior. Re-check offline-only script branches rather than assuming online and offline selection match. [Official offline workflow](https://doc.qt.io/qtinstallerframework/ifw-use-cases-cli.html#creating-custom-offline-installers), [generator implementation](https://github.com/qtproject/installer-framework/blob/aac2cf9c93b80a0f5959ab6c8a00bc378c54fdec/src/libs/installer/packagemanagercore_p.cpp).

## Remaining proof and decision boundary

The metadata contradicts a **four-module payload-only** interpretation: each base bundles extra modules, and its docs/examples dependencies persist in every inspected package script. Report that concrete expansion before authorizing data acquisition. The full Creator GUI is a separate, avoidable candidate rather than a proven mandatory dependency. No official dependency-pruning mechanism was found; rewriting metadata, direct extraction, aqt or vcpkg Qt would change the accepted provisioning mechanism.

This was bounded static inspection, not execution of the pinned Qt installer/controller against a complete frozen repository set. Exact repository enablement, resolved closure, all conditional components, total archive/storage inventory, installed module/Linguist availability and both-platform reconstruction remain open. Ordinary online login and explicit terms/obligation acceptance still require authorization; a local repository/offline artifact does not establish an exemption. No cached credentials were examined. [Official unattended/login requirements](https://doc.qt.io/qt-6/get-and-install-qt-cli.html#providing-login-information).
