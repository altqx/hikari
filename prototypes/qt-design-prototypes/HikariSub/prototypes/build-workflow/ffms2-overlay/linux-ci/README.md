# Linux FFMS2 source-slice execution draft

**Throwaway workflow executed successfully on 2026-09-27; see the [retained run report](ci-run-notes.md) for exact scope.** It extends the [published source recipe](https://github.com/altqx/hikari/blob/43b2b9845addfe94c2c8141c27934f1402568bec/HikariSub/prototypes/build-workflow/ffms2-overlay/README.md) for [Prove pinned CMake workflow provisioning on Windows and Linux](https://github.com/altqx/hikari/issues/48). It does not acquire Qt or libass and requires no Qt credentials or terms action.

## Reviewed process to run

The branch-local workflow runs only on a push to `codex/qt-design-prototypes` touching this directory or its workflow file. Root reviews and pushes; this draft neither dispatches nor publishes a release. Actions are commit-pinned, permission is `contents: read`, checkout credentials are not persisted, and no package cache is restored or uploaded.

1. Start a fresh `ubuntu-26.04` hosted runner. Capture exact image, OS, compiler, CMake/Ninja, libc, package versions and resource snapshots. The image label and live distro repository are mutable; recording them is evidence, not a hermetic-host guarantee.
2. Use the distro package manager to install only NASM with no recommended packages, retaining the simulation and install logs and resolved version. Other named development tools are existing prerequisites; absence fails explicitly. This changes only the disposable runner. Apt metadata/package traffic is separate from the source-acquisition counter and has a ten-minute step bound.
3. Run `cmake --workflow --preset linux-ci-source` in this directory. Before the driver's language-free `project()`, CMake obtains a partial Git checkout of vcpkg commit `ee6a47dac031930715bea2e6dfb9ad60caaa5d83`; verify HEAD and root tree `7312bd1d162dc2b9a2795fb6c9d67e7f364f47c4` plus Git connectivity. Partial clone retains history/trees so the historical FFmpeg port can resolve; needed blobs still transfer and count. This uses Git object identities rather than an unpinned archive.
4. CMake downloads the official `2026-07-27/vcpkg-glibc` executable, checks the overlay lock's SHA-256 and the exact registry's SHA-512, then supplies that executable directly. No repository or vcpkg bootstrap shell script is run. A resolver dry-run is retained before compilation; it may acquire registry metadata and is not build evidence.
5. The driver's build target invokes the **unchanged** parent `cmake --workflow --preset linux-overlay`. That workflow configures the owned release-only static graph, builds the three-frame/private-metadata consumer, and runs its CTest observation. `VCPKG_MAX_CONCURRENCY=2` bounds dependency parallelism; the parent build preset also uses two jobs. Native host triplet is vcpkg's `x64-linux` default; target is `x64-hikari-linux-release`. Resolved host tools/ports, downloads and their digests remain observed results, not assumptions from the inventory.
6. Retain scoped CMake/vcpkg/CTest/apt text logs, statuses, recipe/input hashes, acquired archive hashes, process result and sampled resource measurements for seven days. No executable/library, authored media fixture, dependency archive, cache, credentials or whole environment is uploaded. Root can preserve a sanitized immutable result afterward.

## Resource stops and limitations

There is a 65-minute whole-job limit, a 50-minute source-driver timeout and a 52-minute source-step limit. A two-second CI supervisor samples all non-loopback received bytes after apt and stops the process group at **1.8 GiB received**, **7.5 GiB scratch**, or **less than 10 GiB free disk**. These leave margins against the draft's 2 GiB acquisition / 8 GiB scratch review bounds. Sampling is not a byte-perfect network quota: burst overshoot is possible, other host traffic is conservatively counted, and apt/checkout/artifact-upload traffic is excluded. Disk sampling includes driver, downloads, registry, source/build outputs and logs; final log copies can grow the evidence directory after the driver exits. No memory-performance claim follows from two build jobs. Threshold failure retains available logs and requires review; it does not increase limits automatically.

The CMake driver is this isolated feasibility harness, not the production full-graph provisioner. A successful run establishes only the published specimen's exact assertions. It does not qualify full FFMS2 behavior, audio-option compatibility, an FFMS-only consumer's exported static link closure (the fixture generator links FFmpeg directly), general media capability, Qt/libass composition, deployment, Fedora, or cold/warm/failure-case reconstruction. The FFmpeg 7.1.2 pin remains a compatibility candidate, not a shipping-maintenance selection.
