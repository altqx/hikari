What is sent (for the AI guide and the Site note)

  • A Project key goes only to that provider, in the request's key header, from Qt's relay, exactly like a keychain key. The sidecar sees the placeholder hikari-key; the model never sees a key.
  • .hikari/credentials.toml is never sent: Hikari AI's file tools refuse it, as they refuse .env* and project.local.toml.
  • Environment variables reach no one but the provider they are named for. Hikari AI isn't told their names or values.

Owner questions (reply by number; “yes to all” takes every recommendation)

  1. File name: .hikari/credentials.toml. Beside project.toml, so the Explorer's Project settings node shows it. Recommend yes.
  2. Credentials file shape. version = 1 and a [keys] table of entry names to key strings (state 3). Nothing else is read from it. Recommend yes.
  3. [ai.keys] in project.toml. Keyed by your provider id (openai, anthropic, openrouter-2…, as Settings › AI names them), each { env = "VAR", entry = "name" } with either or both. The environment wins, then the file; when neither has it, yours is used. A provider id you don't have is ignored and shown greyed on the page. Recommend yes.
  4. project.local.toml may set [ai.keys] too, per provider over project.toml's, for one person's own variable names. Recommend yes.
  5. What counts as a value in project.toml: a string, or any field besides env and entry, under [ai.keys]; and a [keys] table (a credentials file pasted in). HikariSub doesn't scan the rest of the file for things that look like keys. Recommend yes.
  6. A value in project.toml (state 6): a closable warning bar in the Project's window, in trusted and untrusted Projects, and a notice on the page with Move to credentials file, which writes the value to the file (creating it and .gitignore if needed) and removes the line from project.toml. Recommend yes.
  7. Untrusted Projects (states 4–5): the existing trust bar also names AI keys, and shows only when a named key is really found; Not now isn't remembered, as today. The page says yours is used. Recommend yes.
  8. Settings › Project › AI (states 1–2): a new AI page on the Project tab with the Keys table, editable fields written by Apply, per-row Use yours, keyless providers greyed. No part of a key is ever shown, not even masked. Recommend yes.
  9. Create credentials file writes both files as in state 3 (mode 0600 on Linux), adds only missing lines to an existing .hikari/.gitignore, and never touches a .gitignore at the Project root. Once the file exists it becomes Open file and Show in folder. Recommend yes.
  10. Environment variables: any name, read from HikariSub's own environment when it starts. The guide says a launch from the desktop doesn't see variables set only in a shell profile. A changed variable needs a restart. Recommend yes.
  11. Scope: provider keys only. Search service keys and the OpenRouter and ChatGPT sign-ins stay yours. The Agent CLIs keep their own logins. Recommend yes.
  12. Never sent. .hikari/credentials.toml joins the [ai] exclude defaults in ADR 0030 now. PJ7 #775, which builds the Project folder grant, isn't merged yet; it starts with the file on that list, and PJ10's test checks no request or sidecar message carries a key or the file. Recommend yes.
  13. ADR 0030 amendment. “A Project can never set … AI providers” stays; a new Keys section says a trusted Project may name keys (this card), never hold them. Recommend yes.
