# Workspace and protected comparison

**Per-Document-tab layouts, 2026-10-18** ([ADR 0020](../../adr/0020-per-document-tab-layouts.md), [WS1 #215](https://github.com/altqx/hikari/issues/215)): each Document tab keeps its own panel arrangement, which replaces the shared arrangement accepted below. The rest of this contract stands: Documents, selection, media context, tool targets and the protected reference keep their ownership rules, and the Workspace still never rewrites subtitles or changes the editing target. Where the text below says the arrangement is shared, the [ownership contract](#ownership-contract) now says how it follows the tab.

Accepted on 2026-09-27: [“shared workspace with optional protected comparison is fine”](https://github.com/altqx/hikari/issues/31#issuecomment-5849397748). Subsequent live reviews chose movable/floating panels (B), follow-editing tools with optional pinning, optional Home, Classic menus/local controls/status, and the named tool/dialog grouping. The default Editing layout follows the current program: video left, audio above the editor on the right, and the subtitle grid across the bottom. Timing, Translation and Typesetting are accepted optional presets. This settles the top-level [information architecture](https://github.com/altqx/hikari/issues/31); detailed comparison navigation continues in [Prototype translation mode and protected comparison navigation](https://github.com/altqx/hikari/issues/49).

The accepted model combines the shared-layout behavior demonstrated by A with an optional protected reference demonstrated by C in the [reviewed prototype](https://github.com/altqx/hikari/blob/163faf7c699c81a12338b04acea9433f356f0814/docs/prototypes/workspace-model.html). The visual baseline is [Compact Studio](visual-language.md). Always-on comparison is not the chosen default. Per-document layouts were not chosen then either; ADR 0020 has since chosen them, per Document tab.

## Default editing arrangement

The user corrected the initial mockup in the live review: **“the default layout should look more like the current program”**, with a screenshot showing video on the left, audio/spectrum above the text editor on the right, and a full-width subtitle grid below both columns. This is the default composition. It supersedes the earlier A-derived full-width audio strip and the prototype opening in a task-specific Typesetting preset.

The default **Editing** preset shows Video, Audio, Editor and Grid together. Start with approximately 44% of the upper area for video and 56% for the audio/editor stack; the audio is the shallow upper section, while the editor takes the remaining right-hand height. The grid spans the workspace width below both. These are adjustable starting proportions, not fixed sizes that clip text or prevent scaling.

Styles, Search, Timing and History remain available movable/floating tools and start closed in this default, leaving the core editing arrangement unobstructed. The Log (NT1, [#302](https://github.com/altqx/hikari/issues/302)) is a panel along the bottom under the others, the whole width, closed in every preset; nothing opens it by itself (View → Log, View → Panels, a toast's Details). The Spellchecker (PU6, [#308](https://github.com/altqx/hikari/issues/308), panel registry 10) is a panel along the bottom too, closed in every preset; Subtitles → Check spelling shows it and starts the check, closing it ends the check. Hiding/showing or rearranging a panel preserves document state. Keep the accepted Compact Studio appearance, application-owned Documents and targets, follow/pin targets and optional Home/protected comparison.

Timing, Translation and Typesetting were subsequently accepted as optional presets; none replaces Editing as the default. The five legacy visibility combinations remain available. The earlier question about making task-preset defaults the primary experience is superseded by the default-layout correction.

| Optional task preset | Visible core panels | Initially open auxiliary tools |
| --- | --- | --- |
| Timing | Audio, Editor, Grid; Video can be opened | Timing, History |
| Translation | Video, Editor, Grid; Audio/comparison can be opened | Search |
| Typesetting | Video, Styles, Editor, Grid; Audio can be opened | — (its own arrangement, below) |
| Karaoke | Video, Template editor, Audio, Grid; the Line editor the tab behind the Template editor | — (its own arrangement, below) |

These are starting arrangements, retaining the accepted hide/show/rearrange/restore behavior and document state. Selecting Translation as a layout does not by itself convert document text or create a protected comparison reference.

**Typesetting is an arrangement of its own (TP1, [#274](https://github.com/altqx/hikari/issues/274), owner-approved [mockup](https://github.com/altqx/hikari/issues/274#issuecomment-6321710762) 2026-10-22).** Timing and Translation are the Editing arrangement with a panel closed; Typesetting is not. The Video panel, with its tool rail and the visual tools' inspector bar, leads the upper row, about two thirds of the window's height, with the **Styles** panel on its right in about a quarter of the width. Below, the Line editor sits at its natural height (its rows whole) on the left, beside a short Grid. Audio is closed; it and the Original text panel (TM1) keep their places above the Line editor, as in Editing. The arrangement is built from the default one the first time Typesetting is shown in a session (`Main.qml` `typesettingLayout()`, asked for and kept by `WorkspaceLayoutController::buildsArrangement`; nothing is built at start), so choosing Typesetting from View > Layout or the layout switcher, on a fresh profile or not, and Reset this layout from it, give it at the window's size. A tab, Session, file or saved layout that already holds a Typesetting arrangement keeps its own panels until Typesetting is chosen again or the layout is reset.

**The Styles panel** (panel registry 7) lists the editing target's Styles in the file's order. Each row draws "Aa" in the Style's font, primary colour and outline colour over a checkered ground, with its name, its font and size, and how many Lines use it; the current line's style carries the edit mark. Enter or a double click applies the chosen Style to the selected Lines, as the Line editor's Style choice does (one undo step). Typing in the list filters it; the commands act on the chosen Style only while the filter shows it, and on that row of the file when it holds two Styles of one name. While the Style manager holds an edit not yet applied, New, Edit, Duplicate, Delete and Copy to the catalog wait for it, and Style manager only brings the window forward. A chosen Style renamed there stays chosen; a Style named "" is listed but not applied (nor does the Line editor's Style choice apply it). Select lines with this style replaces the selection as Select lines' Select mode does: a Style no shown Line uses leaves none selected, the active Line kept. Shown in another tab, the panel keeps its chosen Style where that tab has it, else chooses the active Line's. The header holds Apply to the selected lines, New style, Edit style, Duplicate, Delete and Style manager, icon-only with their names on hover, folding into a More menu when the panel is narrow; the row menu (right click, the Menu key, Shift+F10) adds Select lines with this style and Copy to the catalog…. New, Edit, Duplicate and Copy to the catalog open the Style manager window, which keeps the catalogs and the full Style editor (SY1, [#247](https://github.com/altqx/hikari/issues/247)). The panel is in View > Panels in every arrangement, closed (tabbed with the Line editor) in the others, and follows the editing Document. An arrangement saved before it existed has no place for it, so it opens there tabbed with the Line editor (or on the window's right when the Line editor is closed).

**A preset can carry a mode (TM1, [#232](https://github.com/altqx/hikari/issues/232), owner-approved mockup 2026-10-20).** Translation carries Translation mode. Choosing it from View > Layout or the layout switcher, or choosing a saved layout made from it, for a Document that can take the mode (ASS with a file) and has it off asks once: "Turn on Translation mode for this file?" (Turn on, the default, or Not now). Not now keeps the arrangement without the mode, and the question is not asked again for that Document this session; Subtitles > Translation mode turns the mode on or off from any arrangement and leaves the layout alone. Choosing another arrangement afterwards keeps the mode on. Showing a tab, opening a file (a `TLMode: Yes` file opens in the Translation preset, the mode already on), a Session's arrangement and Reset this layout ask nothing. In translation mode the Original text is a panel of its own, **Original text**, whose header holds Paste all, Paste the selected, Comment out original, Not confirmed and Tags from original (legacy Moving tags, TM1-original-keeps-tags); the Line editor's text field is the Translated text. Like the Reference tray, the panel follows application state rather than the tab: it shows while the editing target's mode is on, where the arrangement keeps its place (above the Line editor in one that never had it), and closes with the mode. The hook is general (`WorkspaceLayoutController::presetMode`): each mode decides what leaving its preset does, Translation keeping the mode on, KP1's Karaoke ([#286](https://github.com/altqx/hikari/issues/286)) putting back the audio mode it replaced.

**Karaoke is an arrangement and a mode (KP1, [#286](https://github.com/altqx/hikari/issues/286), owner-approved [mockup](https://github.com/altqx/hikari/issues/286#issuecomment-6414267025) 2026-10-26, answers [recorded](https://github.com/altqx/hikari/issues/286#issuecomment-6414290303)).** Like Typesetting it is built from the default arrangement the first time it is shown in a session (`Main.qml` `karaokeLayout()`). The upper row holds the Video panel, in Editing's place, and the **Template editor** (KE2) on its right, with the Line editor as the tab behind it. The Audio panel spans the window's whole width under them, so a Line's syllables get every pixel of the waveform. A short Grid, its heading and seven rows, sits at the bottom. Styles, Search, Timing, History, the Original text and the Log stay closed in their usual places. Choosing Karaoke from View > Layout or the layout switcher, or a saved layout made from it, asks nothing (nothing in the file changes). It turns the audio panel's Karaoke mode on, and the Grid's folding of generated Lines. Choosing an arrangement whose preset carries no Karaoke afterwards, in this tab or another and also after a restart (`workspace.karaokeTurnedOn` remembers what Karaoke turned on, [#400](https://github.com/altqx/hikari/issues/400)), puts back only what Karaoke turned on: a mode that was on before stays on, and a Karaoke mode or a folding the user switched while in Karaoke stays as they left it. The Line | Karaoke switch and Fold generated lines work in every arrangement; showing a tab, opening a file, a Session's arrangement and Reset this layout switch neither.

**Folded generated Lines (KP1).** A generated Line is a Dialogue Line whose Effect is `fx` (the karaoke templater's) or `Effector [fx]` (Kara Effector's); a Comment is never one, as the templater neither removes nor regenerates it ([#400](https://github.com/altqx/hikari/issues/400)). With the Grid's **Fold generated lines** on (the Grid's ⋯ menu; the `grid.foldGenerated` setting), each run of consecutive generated Lines shows as one row: the Line numbers it covers, its earliest start and latest end, its Styles and Effects, and "N generated lines" in bold between dashed rules. The row keeps its first Line's place and identity. Clicking it selects every Line of the run, so Delete, Copy and Shift times act on the whole run, and Ctrl+click takes the run out of the selection again. The arrow at the start of its Text cell, or → with the row current, unfolds the run; the arrow, or ← on its first row, folds it again (there the Grid takes them over the Previous and Next frame hotkeys; elsewhere they keep their usual meaning). Folding a run over the active Line leaves its first Line active with the run selected. Turning Fold generated lines on folds every run, and turning it off shows every Line. Folding only hides rows: the Lines stay in the file, play on the video and count as selected rather than hidden, and commands over the selection (Paste columns, Delete text and the like) act on every Line a folded row stands for. A folded row shows while any of its Lines passes the Grid filter; its Lines the filter hides stay hidden. It also carries the hidden-block mark after the run, which reveals or hides that block as on any row. Turning Fold generated lines on selects each run whole or not at all, as its first Line is. After that, a selection that reaches a folded run only in part unfolds it, so a folded row always stands for a run selected whole or not at all: Find or the audio's next Line landing on one of its Lines, or another panel making one active.

Runnable references for this correction: [Editing workspace](https://github.com/altqx/hikari/blob/2dc12567c66f79d5d0a74d4b3356082c55566b30/docs/prototypes/workspace-tools.html), [run/review notes](https://github.com/altqx/hikari/blob/2dc12567c66f79d5d0a74d4b3356082c55566b30/docs/prototypes/workspace-tools-notes.md) and [capture](https://github.com/altqx/hikari/blob/2dc12567c66f79d5d0a74d4b3356082c55566b30/docs/prototypes/workspace-tools-preview.png). Browser checks confirmed the full-width grid, panel recovery retaining selection, and Video → Audio keyboard traversal; native docking remains a separate gate.

## Ownership contract

Each Document tab has its own Workspace (ADR 0020). Switching tabs changes displayed content, selection and media context, and shows that tab's panel arrangement: its docked, tabbed and floating panels at their sizes, in the same main window, which keeps its geometry. A tab opened or created starts with the Translation preset when its file has `TLMode: Yes`, otherwise with a copy of the current tab's arrangement; opening a file into the current tab counts as opening it. Presets, saved layouts, Reset this layout and the layout backup change the current tab only; a preset, like a saved layout, is applied in place, so the main window keeps its size (TP1); saved layouts are the user's own arrangements, kept under a name for every tab and across restarts (WS3, [docking contract](../docking.md#save-restore-and-recovery)). The Session saves each tab's arrangement, and so does an ASS or SSA file, in its `[Hikari]` section, when it is saved (WS2, "Save panel layout in subtitle files", on by default), with the preset or saved layout it started from; opening the file gives its tab that arrangement, a restored Session's own taking precedence. A tab whose saved arrangement is invalid or restores only in part shows the Editing preset with a notice ([docking contract](../docking.md#save-restore-and-recovery)). A workspace change rearranges tools; it does not rewrite subtitles, switch their format or discard a draft. Panels that follow application state rather than the tab stay with that state: the Reference tray shows with the Grid while there is a comparison, whichever tab's arrangement is shown.

Each document retains its own selection and associated media context. The editing target identifies the document receiving content-changing commands. Keyboard focus can visit other UI regions without implicitly changing that target.

Comparison is optional. Its protected reference can be read, selected and copied, but editing commands cannot mutate it. The UI must distinguish editing target and reference through explicit labels as well as visual treatment. An explicit operation can make the reference the editing target; existing content and per-document context survive that change. Reference focus alone is insufficient.

Translation mode remains a document capability with original/translated text and confirmation semantics. It is not replaced by opening a second document for comparison. Existing comparison criteria—time, visibility, selection and styles—remain capabilities to design; the ownership decision does not drop them.

## Movable and floating panels

Accepted in the live tool-placement review: **B / movable and floating panels**. Tools can be rearranged, hidden, restored and detached from the main workspace. Preserve keyboard-accessible placement actions alongside pointer interactions. Each Document tab keeps the arrangement chosen in it (ADR 0020).

The [reviewed HTML follow-up](https://github.com/altqx/hikari/blob/9781b3cb51fb87d9640366a9619b9c5589ff1e26/docs/prototypes/workspace-tools.html) illustrates Left/Right/Bottom and Float positions. Its floating cards stay inside the browser page; this acceptance chooses the UX capability, not that simulation as a native implementation. The [accepted native docking contract](../docking.md) selects KDDockWidgets behind Hikari’s adapter, including persistence/recovery and cross-window ownership. Native accessibility, monitor and Qt integration qualification remain required.

## Persistent tools and Home

Accepted in the live review: Styles, Search, Timing and History **follow the editing document by default**, with an **optional Pin current document** control. A pinned tool retains its named document across editing-tab changes. When that document is a protected comparison reference, content-changing Apply remains unavailable. A tool must expose its document and scope; a preview must not silently retarget when the document or selection changes.

The sample permits a deliberately pinned tool to apply to an inactive, unprotected document after showing that target in Preview. Treat a tool's explicit target separately from the application's editing target; general editing shortcuts still use the editing target. Review detailed per-tool scope, confirmation and stale-preview rules in their surface tickets.

**Home is optional**, with the workspace as the normal editing destination. Home provides recent-file and recovery entry points without discarding the open documents or their arrangements. It is not a mandatory start screen. Actual startup/session restoration, file recovery and unsaved-close flows retain their data and lifecycle contracts.

**Home page (SH2, [#221](https://github.com/altqx/hikari/issues/221)), owner-approved mockup 2026-10-19.** Home is the main area's content while no Document is open (a protected reference counts, its tray needing the panels), and only then: at start without subtitles, after the last tab closes and after Close all tabs. There is no Home tab to return to while Documents are open, and the Document tab bar is empty while it shows (keeping its height, so the panels do not resize when a Document opens). It covers the docked panels, which keep their layout but take no input; F6 stays on the page. From the top, within 24 margins and at most 1120 wide, centred:

- **New** (the accent button, an Untitled Document as Ctrl+T makes), **Open…** and **Open video…** (File's commands; media opened with no Document opens in a new Untitled one).
- **Last session**, only when the last session has a Document with a file: how many and their names, with **Restore** (File > Last session > Load last session, with its review). The startup prompts are unchanged.
- **Recent files**: the recent subtitles list (up to 20), name over path (middle-elided), the last-opened time ("Today 23:41", "Yesterday 18:52", then the date), a **Filter** field. A missing file keeps its row, marked **Missing** in the warning colour, cannot be opened, and has **Remove**; Delete removes the current row; the row's menu has Open, Show in folder, Copy path, Remove from list and Remove missing files. Show in folder also shows on the hovered row. An empty list says "No recent files".
- **What's new** (SH3, [#223](https://github.com/altqx/hikari/issues/223), owner-approved 2026-10-21): a 320-wide column on the right (under the list below 1000 wide, 200 tall), "What's new" with "Since <version>", the GitHub release notes of the versions after the one run before up to the installed one (newest first, at most ten, then "And N earlier versions: all release notes"), and **All release notes** (GitHub's releases page). Each version: its name, a **Pre-release** badge, its date, its notes as plain rich text (headings as section labels, links in the accent colour opening the browser, http(s) only; no raw HTML, no images loaded, an image's alt text instead). It shows only while there are notes: hidden on a first fetch, offline with nothing cached, or with "Check for updates automatically" off and nothing cached. A first start, or the first start after the legacy app, shows the installed version alone. The channel is the update check's (pre-releases only on Beta, or on a pre-release build).
- **Help > What's new** (between Check for updates and About, no hotkey): the same notes on the dialog frame, modeless and resizable, "Changes since version <V>, the one you used before.", All release notes and Close. Opening it reads the list when nothing is cached and update checks are on; with none to show it says why (checks off, fetching, the fetch failed, none for this version). There is no popup after an update.

Keyboard: the list has the focus when it has a file (else New); Tab order New → Open… → Open video… → Restore → Filter → the list → What's new; Up/Down/Home/End move, Enter opens, Delete removes, the Menu key or Shift+F10 opens the row's menu. The list is "Recent files"; a row reads "name, path, last opened time" and ", missing" for a missing file. Departures: SH2-last-tab-home and SH2-recent-opened-and-missing in [compatibility-decisions.md](../compatibility-decisions.md).

## Shell commands, properties and task grouping

Accepted in the live follow-up on 2026-09-27: **Classic menus and local controls**, plus **the proposed tool/dialog grouping**. The [reviewed Classic shell](https://github.com/altqx/hikari/blob/ae07d2de29157c5a131cfed28fa207f70e778bac/docs/prototypes/shell-chrome.html) retains traditional top-level menus, controls attached to their owning panels, line properties beside the text editor and detailed media/status information across the bottom. A contextual right inspector and compact shared command strip are not the default. Individual commands remain discoverable through the shared action system and keyboard routing; the sample menu subset does not remove unshown commands.

Styles, Search, Timing and History are persistent tools that can stay open while editing, following the accepted movable/floating and follow/pin rules. Timing here means shifting/postprocessing; it does not replace the Audio panel. History is document edit history. Search/find/replace/select-lines/results keep explicit scopes; Styles retains document styles and external catalogs as distinct collections. Their individual prototypes and accepted placements are indexed in [reviewed surface layouts](reviewed-surface-layouts.md); remaining behavior is tracked separately.

Script properties, Resample, Font collector, MKV extraction, Preferences and script-created options use task dialogs. This grouping does not require long operations to block the UI: collection/extraction keep progress, cancellation and inspectable results. Script dialogs preserve their schema/API contract. The subsequent Automation review selected a persistent manager tool. Other unreviewed behavior remains separate; this acceptance does not adopt every row of the older placement worksheet.

The [Classic capture](https://github.com/altqx/hikari/blob/ae07d2de29157c5a131cfed28fa207f70e778bac/docs/prototypes/shell-classic-preview.png) records the reviewed structure. Browser observations cover sample menu/dialog entry, Escape dismissal, context/tool switching, F6 from editor to Grid and the full-width Grid in both alternatives. Native menus, focus, accessibility, task lifetimes and full per-surface behavior remain future verification.

## Captured interaction evidence

The HTML study demonstrates shared versus per-document layout retention, protected reference content while the editing target changes, panel restoration, recovery as a separate copy, a zero-document state, missing video while subtitle editing remains available, and save/discard/cancel close choices. Save and media relinking are simulated in memory. F6/Shift+F6 traverse the demonstrated major panels, including from text/grid focus.

These demonstrations clarify the ownership model. They do not establish real file/session compatibility, native docking, screen-reader behavior, decoding, persisted workspaces or a final save policy.
