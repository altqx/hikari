# Proposed compatibility and legacy-defect policy

For [Define observable compatibility and the legacy-defect policy](https://github.com/altqx/hikari/issues/38). **Policy accepted on 2026-09-27: individually approved fixes become default. Only the subcases in the [approved-departure ledger](../compatibility-decisions.md) have subsequent approval.** The authoritative [compatibility contract](../compatibility.md) records the accepted rule; this retained review artifact supplies its candidate ledger. Evidence: corrected [core inventory](https://github.com/altqx/hikari/blob/5d392a10c98b97c9b2b92f4b3f9dc49cd429752c/docs/research/core-inventory.md), [data inventory](https://github.com/altqx/hikari/blob/1eea34cd5db8db276f2e71cdff3f43f345cefd5b/docs/research/data-inventory.md), [UI inventory](https://github.com/altqx/hikari/blob/6f91fd28eab4c42d2c00f848606b47585c2b6bc8/docs/research/ui-inventory.md) and [Lua-host research](https://github.com/altqx/hikari/blob/a99a2470e958437290de73dd2451ee57cc763336/docs/research/lua-automation-host.md). These are static findings and characterization plans, not executed parity results. Their recommendations do not authorize departures.

## Commitments and proposed approval rule

Existing subtitle files, style/font catalogs, sessions/autosaves and Lua scripts must work as-is. Read/import must leave original files unchanged. Settings and hotkeys receive one-shot migration, preserving scope, identities and unresolved entries. **Legacy themes, color mappings and `PROGRAM_THEME` are excluded already.** Preserve authored rules/dictionaries. Rebuild the core in the big-bang rewrite; parity does not require wrapping old wx classes.

Every inventoried capability remains in scope unless the user explicitly approves its merge or removal. A merged surface must retain operations, command scope and discoverability. A painted renderer or accepted visual design is not approval to remove behavior.

| Proposed class | Acceptance and approval rule |
| --- | --- |
| Required compatibility | Default for documented workflows, data meanings and working script behavior. Implementation may change internally; observable differences need another class and explicit approval. |
| Explicit defect fix | A named ledger entry must show trigger, old evidence, desired outcome, affected users/scripts/data and fixtures. Only an explicit user decision naming the entry, or enumerated batch, approves its departure. “It is a bug” is insufficient. |
| UX redesign | Obtain reaction to a concrete prototype and record precisely which interactions changed. Visual approval does not authorize altered serialization, script APIs or command results. Trace any merge/drop to named capabilities and its approval. |
| Unsupported input / recovery | Record a bounded unsupported case, diagnostic, preserved raw input and a usable recovery/relink/export path. Explicit user approval is needed before rejecting formerly accepted input or dropping information. Missing dependencies must not masquerade as corrupt documents. |

An unexplained difference fails parity review. Suspected crashes or data loss are not automatically golden requirements: characterize them without risking originals and leave their disposition unresolved until reviewed. Do not silently substitute upstream Aegisub semantics for observed HikariSub behavior.

## Evidence and minimum decision

Each ledger record needs source commit, fixture hash/provenance, platform/runtime/dependencies, steps, old observed output, proposed expected output, comparison rule and exact approval link. Keep bytes, semantic document state, script returns/errors, undo/selection and rendered pixels separate. Record unexecuted or inconclusive cases explicitly. Retain old characterization when a new expectation is approved.

**Accepted policy choice:** individually approved defect fixes change the default behavior. This does not approve C01–C08 wholesale. Release scheduling and performance budgets remain separate decisions.
