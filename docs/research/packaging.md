# Packaging, signing and updates for the Qt rewrite

Research for [#39](https://github.com/altqx/hikari/issues/39), completed 2026-09-27. This report inspects repository code and primary documentation; it does not build a release package, provision an account, sign binaries or publish a release. Recommendations below remain decisions for the rewrite.

## Summary

Use one audited, relocatable staging tree to produce a **Windows portable ZIP and an offline installer**. Inno Setup is a reasonable first installer candidate; keep the existing download-page notification behavior initially. Automatic installation is a separate capability: WinSparkle plus signed installer downloads, MSIX/App Installer, and Qt Installer Framework are feasible alternatives with different ownership and update models.

For first-class Ubuntu/Fedora support, prototype **Flatpak as the managed installation/update channel and AppImage as the portable channel**. Neither label proves compatibility: both need actual media, font, file-dialog, GPU and audio tests on the supported distributions. Preserve a tar staging artifact for diagnostics. Native DEB/RPM packages are possible but introduce additional per-distribution maintenance; they are not automatically generated correctly by renaming the tarball.

Separate immutable program files from writable configuration/cache before implementing any installer. Keep file associations and the current update checker as parity features. Qt runtime plugins are deployment dependencies, not authorization for a general third-party plugin ecosystem.

The existing GPL-related comments need correction in the rewrite's dependency specification: being a GPL app does not require enabling GPL components in FFmpeg, and excluding x264/x265 is not needed merely to avoid imposing GPL terms on an already GPL program. ## Qt and media deployment

Use `install(TARGETS)` plus [`qt_generate_deploy_qml_app_script`](https://doc.qt.io/qt-6/qt-generate-deploy-qml-app-script.html) for the selected Qt version, with a clean install prefix. It handles QML import deployment; the related [runtime-dependency command](https://doc.qt.io/qt-6/qt-deploy-runtime-dependencies.html) handles linked libraries/plugins but not QML imports itself. Current Linux behavior excludes system-library locations by default. A distro-installed FFMS2/libass is therefore not automatically bundled just because the executable links it. Windows/macOS use their Qt deployment tools, so non-Qt libraries need an explicit manifest. Dynamic `dlopen`/LoadLibrary dependencies and runtime-selected QML imports also need explicit inventory and execution coverage.

On Windows, [`windeployqt --qmldir`](https://doc.qt.io/qt-6/windows-deployment.html) scans QML imports and assembles Qt libraries/plugins/translations. Keep the matching Qt build's platform, image, TLS, multimedia and QML modules as applicable; use relative `qt.conf` paths rather than the developer SDK path. Do not copy an entire Qt SDK to compensate for an incomplete manifest. Test startup with Qt removed from PATH and all developer environment variables unset.

The staging manifest should include FFMS2 and its FFmpeg ABI family, libass and its actual font/shaping dependencies, chosen audio output, Hunspell dictionaries, resources, translations, notices and exact source/build metadata. Whether FreeType/Fontconfig/DirectWrite/HarfBuzz/FriBidi are linked varies by build. Inspect the actual binaries rather than assume one global list. If Qt Multimedia and FFMS2 require incompatible same-named FFmpeg DLLs, settle version alignment or process isolation before packaging; merely copying both sets into one directory is not a solution. GPU drivers and OS runtime components belong to the platform contract.

For the installed Windows build, prefer the supported Visual C++ Redistributable installer. For portable output, Microsoft explicitly documents [licensed app-local deployment from Visual Studio's redist directory](https://learn.microsoft.com/en-us/cpp/windows/choosing-a-deployment-method?view=msvc-170). Qt's current Windows page cautions against redistribution of arbitrary developer-machine DLLs. These are reconciled by using the licensed redist set and its terms, not copying System32 or random build-machine files. App-local CRT security servicing becomes the package maintainer's responsibility.

Proposed layout: immutable executable/libraries/Qt plugins/QML/resources; normal settings, recovery files and media caches through [`QStandardPaths`](https://doc.qt.io/qt-6/qstandardpaths.html); optional explicit portable marker/config switch that redirects writable state into the portable directory. Refuse or explain an unwritable portable location rather than silently losing changes. Migrate legacy `Config` by a deliberate copy with rollback; uninstall must not silently remove user subtitle files or portable data.

Keep the GPL application's corresponding source, build scripts, dependency patches/configurations and notices available with each release. Qt modules have different license offerings—check the chosen set in [Qt Licensing](https://doc.qt.io/qt-6/licensing.html), not just the headline Qt license. Dictionary/font licenses belong in the manifest too. Source availability and operating-system signing serve different purposes.

## Windows installer and update choices

| Option | Why it fits | Cost or constraint |
| --- | --- | --- |
| Inno Setup EXE + ZIP | Reuses the staged tree; per-user or administrative installs, shortcuts, registry entries, uninstall and signing hooks. An offline full installer is straightforward. | Upgrade/migration policy and updater are separate work. Preferred first candidate for this app. |
| WiX MSI / Burn | Windows Installer integration, repair and managed deployment; Burn can chain prerequisites. | More component/upgrade authoring and maintenance. Worth considering if enterprise MSI requirements exist. |
| Qt Installer Framework | Offline/online component installers plus a maintenance tool and repository updates. | Own component repository/versioning/maintenance-tool lifecycle. Useful for a genuinely componentized installation, excessive solely to preserve the existing notifier. |
| MSIX + App Installer | Package identity, managed install/uninstall and OS-driven update checks/repair. Full-trust desktop packaging is possible; MSIX is not synonymous with a UWP rewrite. | Trusted package signature/publisher identity, manifest associations, OS policy and read-only package contents. Separate ZIP remains needed for portable use. |
| WinSparkle + ordinary installer | Native updater library with appcast discovery and EdDSA verification; can deliver the same full installer. | New signing key/appcast lifecycle, shutdown/unsaved-document coordination and install/rollback tests. Use only if automatic download/install is explicitly selected. |

Primary references: [Inno Setup features](https://jrsoftware.org/isinfo.php), [WiX documentation](https://docs.firegiant.com/wix/using-wix/), [Qt IFW overview](https://doc.qt.io/qtinstallerframework/ifw-overview.html), [MSIX runtime model](https://learn.microsoft.com/en-us/windows/msix/desktop/desktop-to-uwp-behind-the-scenes), [App Installer update/repair](https://learn.microsoft.com/en-us/windows/msix/app-installer/auto-update-and-repair--overview), and [WinSparkle README](https://github.com/vslavik/winsparkle/blob/master/README.md). Inno's site requests commercial users purchase a license; tool licensing/support costs should be checked against the owner's intended use rather than assuming every installer tool has identical terms.

Recommendation: start with an offline, per-user Inno installer plus ZIP and the parity notifier. Offer associations as an option and register as an eligible handler; changing the user's default is controlled by Windows, not by overwriting protected defaults. See [Microsoft Default Programs](https://learn.microsoft.com/en-us/windows/win32/shell/default-programs). Keep stable/prerelease preference, reminder and disabled-check behavior; validate release metadata/URLs and distinguish a failed check from “up to date.” A package-managed install should route to its manager rather than have an internal updater overwrite its files.

If self-update is later chosen, require channel/architecture/package-kind matching, authenticated metadata/artifact verification, a bounded download, safe process exit, interrupted-install recovery and settings migration. A SHA-256 file beside a download detects corruption but does not establish publisher authenticity by itself. Authenticode and an updater's EdDSA key address different trust paths.

## Ubuntu/Fedora: Flatpak versus AppImage

| Property | Flatpak | AppImage |
| --- | --- | --- |
| Runtime | Pinned platform/runtime with app dependencies under `/app`; Qt guide recommends KDE runtime. | AppDir image carries selected libraries; host kernel/graphics/ABI baseline still matters. |
| Files/media | Sandbox and portals; selected-file access may not imply access to sibling video, fonts, project files or writable sidecars. | Normally has the launching user's filesystem access; simpler traditional file workflows. AppImage itself is not a sandbox. |
| Updates | Flatpak repository/desktop manager owns updates, version history and runtime updates. | Embed update information and optionally use AppImageUpdate; otherwise replace the file. |
| Desktop | Desktop/AppStream/MIME exports integrated with installation. | Optional integration; a moved executable must not leave stale launcher/association paths. |
| Offline | Must include/install the runtime and required extensions as well as app content. A lone bundle is not always self-contained. | Self-contained application payload once downloaded, subject to host compatibility and runtime mount/extraction support. |

Flatpak's [Qt guide](https://docs.flatpak.org/en/latest/qt.html) and [sandbox permissions](https://docs.flatpak.org/en/latest/sandbox-permissions.html) provide the concrete mechanisms. Prototype Wayland plus fallback X11, GPU access and playback audio permissions, adding networking only for an intended online feature. Avoid treating broad home access as an invisible workaround. Test “open ASS, find sibling video/font, reopen recent project, atomic save, write FFMS index/cache, drag/drop, removable disk” explicitly. Cache/index files may need to live in application cache with a media identity key rather than beside read-only media.

Flatpak exposes system and user font directories under `/run/host/...`, but **does not expose the host's Fontconfig configuration files**. Thus “fonts are visible” does not prove identical fallback or libass rendering. Verify installed fonts, attached Matroska fonts and explicitly selected project fonts independently. [Desktop integration/fonts](https://docs.flatpak.org/en/latest/desktop-integration.html) documents the mapping. Ship the selected FFmpeg/libass capabilities in the app/runtime contract; do not assume random host codecs are visible or that every runtime includes the required codec set.

AppImage [concepts](https://docs.appimage.org/introduction/concepts.html), [runtime architecture](https://docs.appimage.org/reference/architecture.html) and [FUSE troubleshooting](https://docs.appimage.org/user-guide/troubleshooting/fuse.html) show why a single file is not a universal compatibility guarantee. Pin the AppImage runtime/tool revision and choose the oldest supported userspace baseline deliberately. Test both Ubuntu and Fedora with no SDK present, plus FUSE/mount restrictions and extraction fallback. A newer glibc-built program does not become compatible with older hosts by putting it in SquashFS. Keep host driver boundaries intact rather than blindly bundling every `ldd` result.

AppImage [update information](https://docs.appimage.org/packaging-guide/optional/updates.html) can identify a `.zsync` endpoint; this is update discovery/delta machinery, not an automatic trust policy. [Embedded signatures](https://docs.appimage.org/packaging-guide/optional/signatures.html) require external validation; printing an embedded signature is not verification. Flatpak's [repository hosting](https://docs.flatpak.org/en/latest/hosting-a-repository.html) uses signed repository metadata and configured trust. Choose Flathub submission versus an owner-operated repository; do not make two independent updaters compete.

## Signing prerequisites and owner decisions

- **Windows:** choose a publisher identity and eligible signing route: commercial CA certificate/HSM, Azure Artifact Signing, or an accepted open-source program. Microsoft's [current comparison](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options) lists Artifact Signing around US$9.99/month and geographic eligibility restrictions; neither cost nor eligibility is assumed approved. [SignPath Foundation](https://signpath.org/) offers qualifying open-source projects free signing, subject to application/acceptance. A certificate does not promise immediate SmartScreen reputation. Self-signed development trust is not a public distribution solution.
- **Signing operations:** owner controls account verification, billing, certificate/key custody, recovery/rotation and CI signing authorization. Use a restricted release environment with short-lived identity where supported; never expose signing credentials to ordinary untrusted PR builds. Sign after deployment tools have patched binaries and before final checksum publication; timestamp and verify signatures on final packages. No accounts or keys were created here.
- **Linux:** an owner-operated Flatpak repository/AppImage update channel requires repository/key ownership and trusted public-key distribution. Flathub has a submission/maintenance workflow instead. Hosting/storage and release operations still have costs even without a CA certificate purchase.
- **Later macOS:** make a relocatable `.app` with `macdeployqt`, audit nested libraries and entitlements, sign with Developer ID and hardened runtime, notarize using current Apple tooling and staple the ticket before distributing DMG/ZIP. This needs macOS build/test capacity and owner credentials. Apple documents [Developer ID/notarization](https://developer.apple.com/developer-id/) and [US$99/year enrollment](https://developer.apple.com/programs/enroll/) (regional pricing/waivers vary). LuaJIT or native automation may affect entitlements; a successful Windows package does not resolve that. No Mac package or notarization was tested.

## Offline/reproducible packaging and release checks

Proposal: split **fetch → build → stage → verify → sign → publish**. Cache verified source archives, Qt SDK/compiler inputs and dependency manifests first; then rebuild and stage with network disabled. Pin Git submodule commits, tool/container versions, runtime/SDK commits and all downloaded assets. Flatpak builder supports [`--download-only`, `--disable-download`, `--export-only` and source bundles](https://docs.flatpak.org/en/latest/flatpak-builder-command-reference.html), which fit that separation. An offline installer must contain required runtime payloads or clearly state its external prerequisite.

Normalize ordering/timestamps/permissions and avoid embedding workspace paths. Compare unsigned staged content and build metadata from two clean builds; timestamped signatures/notarization are separate nondeterministic envelopes. Do not call a package reproducible solely because its tar headers are normalized. Store the manifest, hashes, source bundle, toolchain/configuration and symbols with each release.

Before a release, the concrete CI/runtime gates should be:

1. Fail for missing runtime assets and unintended build-machine paths. Audit PE/ELF/Mach-O dependencies, Qt/QML plugins and dynamically loaded helpers; launch on clean target machines with no Qt SDK.
2. Open/save ASS with non-ASCII/spaced paths, libass font fixtures and attached fonts; decode/audio-play representative media; exercise selected Qt rendering backends, IME and accessibility basics. Headless startup alone is insufficient.
3. Install/upgrade/uninstall and portable relocation; existing config/recovery migration; ordinary-user/read-only locations; file association registration; stable/prerelease/missing-network behavior. Verify user subtitles survive uninstall and rollback.
4. Test Ubuntu and Fedora Wayland/X11 plus Windows target architectures; test Flatpak portals/permissions and AppImage runtime restrictions separately. Add macOS only after its complete runtime/signing checks exist.
5. Validate final signatures/hashes and channel/architecture metadata; verify corresponding-source availability. Publish only the exact verified staged artifacts. This report did not execute these gates.
