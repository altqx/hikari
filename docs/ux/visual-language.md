# Compact Studio visual language

## Status and evidence

**Accepted design baseline: D / Compact Studio.** The initial approval combined C's compact technical presentation with A's panel arrangement; the later live correction changes the default arrangement to match the current program, as described below. The user first wrote, **“I like the compact design of C and the lay our of A”** ([26 September 2026](https://github.com/altqx/hikari/issues/32#issuecomment-5848973463)), then replied **“LGTM”** to the completed study ([26 September 2026](https://github.com/altqx/hikari/issues/32#issuecomment-5849386836)). That approval covers the reviewed appearance, component gallery and document-tab example; the later instruction revises the default composition. It does not need another design-direction approval.

The initial immutable appearance reference is [`visual-language.html` at `163faf7c699c81a12338b04acea9433f356f0814`](https://github.com/altqx/hikari/blob/163faf7c699c81a12338b04acea9433f356f0814/docs/prototypes/visual-language.html), using `variant=D`. Its [README](https://github.com/altqx/hikari/blob/163faf7c699c81a12338b04acea9433f356f0814/docs/prototypes/README.md) describes a throwaway study; any wording there awaiting review predates the linked LGTM. This specification records the approved reference and its limits rather than promoting the HTML implementation into production code.

HikariSub owns the Qt application layer under [ADR 0001](../adr/0001-hikari-owned-qt-layer.md). The vocabulary of **workspace**, **editing target** and **protected reference** comes from [CONTEXT.md](../../CONTEXT.md). Panel membership, workspace ownership and document behavior belong to the [workspace specification](workspaces.md); this document defines their visual and interaction presentation.

## Composition

Compact Studio has quiet, nearly square boundaries, close panel spacing, a compact command area and monospaced tabular data. The default editing scene follows the user's current-program screenshot: video at the left, audio/spectrum above the line editor at the right, and the subtitle grid spanning the full width below both. The latest layout instruction supersedes the initial A-derived full-width audio strip while retaining Compact Studio appearance and movable/floating panels.

Use approximately 44% / 56% for the default upper split, with a shallow audio region above the right-hand editor and a substantial full-width grid below. The [workspace contract](workspaces.md) defines this Editing preset and the initially closed auxiliary tools. Treat prototype CSS measurements as review proportions, not application minimum sizes; allow resizing and system text/scaling without clipping controls.

The study header, A–D comparison switcher, direction badge, study guide, review question and debug/status narration are review scaffolding. The component gallery is a specification aid, not a new product screen. Synthetic scenery, waveform and playback demonstrate composition only.

The [revised D study](https://github.com/altqx/hikari/blob/2dc12567c66f79d5d0a74d4b3356082c55566b30/docs/prototypes/visual-language.html) and [capture](https://github.com/altqx/hikari/blob/2dc12567c66f79d5d0a74d4b3356082c55566b30/docs/prototypes/compact-studio-preview.png) implement the current-program arrangement. The earlier immutable study remains the provenance for the approved appearance and component gallery.

**Panel header: the dock header row (2026-10-05, D3 2026-10-06).** The D study draws a header inside each panel. With docking, each panel also has a dock title bar, so the two repeated the same title. The user reviewed the Classic shell on 2026-10-05 and dropped the in-panel header. The dock header is now each panel's only header. A panel keeps its accessible name (the Grid's description names the editing target). The document name appears only where it adds information: the Document tab and the window title. The Grid shows the active tab's Document, so it does not repeat the name. The Protected reference has no Document tab, so its tray's dock is titled "Reference: <name>". The status bar does not name the editing target: its first field is legacy's help and Automation status text. [D3](https://github.com/altqx/hikari/issues/207) gave the dock chrome MuseScore 4's form ([research](../research/musescore-docking.md), [docking.md](../docking.md#chrome)): one header row per panel group. A lone panel shows a title bar, its title in bold and a "⋯" button, in the panel body's colour (`field`, the Panel's `base`). A group of tabs, and the Grid, the Reference tray and Search even alone, show a tab bar only, on the `raised` strip: the selected tab is in the body's colour and bold with no line under it, the others `raised` in regular weight with 1-pixel `line` separators, a hovered one the body's colour at half strength; there is no accent underline. The current panel's toolbar sits right of the tabs (the Reference tray's navigation), with no close button: a header's only close is its "⋯" menu's. Tabs that do not fit keep the selected one whole and fade the others out over their last 20 pixels. The header shows the move cursor, its buttons the arrow. Panels have no frame of their own: 1-pixel `line` separators part them. The accent appears in the dock chrome only as drop feedback while a panel is dragged (a 1-pixel border and a 30 % fill over the area it would take). A floating panel is a borderless window framed in the body's colour with a 1-pixel `line` boundary, 3-pixel corners and a drawn shadow, on every platform. The group holding the focus rings its header in the `focus` role (see Keyboard focus).

## Hikari theme layer (K2)

The user decided on 2026-10-05 to follow MuseScore 4's appearance model ([research at v4.7.5](../research/musescore-appearance.md)) with no per-colour editing. [K2](https://github.com/altqx/hikari/issues/206) implements it as the Hikari theme layer, `src/ui/theme.h`: one set of the roles above, resolved from the chosen appearance and exposed once. QML reads the `Theme` singleton (`Theme.panel`, `Theme.accent`, ...); the Qt Quick Controls draw with the application palette the layer sets, in the `HikariStyle` controls style (`src/ui/style`: Fusion on every platform, since the native Windows style draws with the system's colours, with every control outline in `line`, keyboard focus drawn as the 1-wide focus ring below (`FocusFrame`, in `focus` from `StyleColours`, which the layer sets with the palette), and a focused field's border from the accent; Fusion's own outline, its window colour darkened 140%, measures about 1.1:1 against the Dark and High contrast black panels, so fields and buttons lost their boundaries there; `hikari_ui_theme_tests` controlsOutlineInTheBoundaryColour, keyboardFocusRingInTheTextColour); controls the shell draws itself take `FocusRing`, the same ring (the Appearance page's cards and swatches); the icons take `IconTheme`'s colours, which are the layer's; owner-drawn items (the Grid, the audio display, the spelling marks) read the layer's roles and content colours and repaint when it changes.

**Themes.** Light, Dark, High contrast white and High contrast black (`appearance.theme`: `light`, `dark`, `highContrastWhite`, `highContrastBlack`; Dark by default, legacy's default theme). High contrast black is the spec's high-contrast column; High contrast white is drawn to match it on white.

**Follow system theme** (`appearance.followSystem`, on by default). While on, Light or Dark comes from the platform's colour scheme (`QStyleHints::colorScheme`, live: the Windows setting, the XDG desktop portal on Linux); it never turns high contrast on or off, it only moves a high-contrast theme to its matching side (white for a light scheme, black for a dark one). An unknown scheme keeps the chosen theme. Choosing a theme by hand turns following off.

**Window title bars.** On Windows the title bar Windows draws on a framed window (dialogs and tools in their own windows, and the main window with "Use system title bar"; floating panels and the main window's own title bar are frameless) follows the shown theme: dark under Dark and High contrast black, light under Light and High contrast white, whether the theme follows the system or is chosen in Options, and live on every switch (`src/ui/title_bars.h`, `DWMWA_USE_IMMERSIVE_DARK_MODE`). While the theme does not follow the system, Qt is asked for the theme's side (`QStyleHints::setColorScheme`, on Windows only), so that what Qt sets on a frame itself agrees. Other window systems draw their decorations from the desktop's own theme, and Qt's colour scheme is left to the system there.

**The main window's title bar (SH1, [#220](https://github.com/altqx/hikari/issues/220)).** After MuseScore 4's (MS1): one 32-pixel row on `panel`, left to right the application icon (16 px in a 32-pixel square), the menu titles (8 on each side, 24 high), the layout switcher 8 after them (`raised` with a 1-pixel `line` boundary, `select` with an `accent` boundary under the pointer and while open), the window's title and the window buttons (46 × 32: Minimise, Maximise or Restore, Close; IC1's 16-unit glyphs). A menu title is `raised` under the pointer and while its menu is open; Minimise, Maximise and Close are `raised` under the pointer and a shade darker pressed (the high-contrast themes: `select`, with a 1-pixel `line` ring), Close included (no red). While the window is not active the titles, the title and the glyphs take the `disabled` role and the icon 55 % opacity. The title centres on the window when it clears the switcher and the buttons by 32 pixels, else in the room between them, elided, and is not shown under 80 pixels; a still narrower window folds the last menus into More (⋯). The keyboard on the menus (Alt alone, F10) rings the current title or the switcher in `focus`, 1 wide, on `raised`, and underlines the menus' letters, which also show while Alt is held and never otherwise. In the high-contrast themes a 1-pixel `line` parts the row from the Document tabs. On Wayland and X11 the frameless window has a 1-pixel `line` boundary while not maximised and no drawn shadow; Windows draws its own shadow and boundary. With "Use system title bar" the window system's frame stays and the row, 27 high, holds the menus and the switcher only.

**Dialogs (DG1, [#222](https://github.com/altqx/hikari/issues/222)).** One frame for every dialog, `src/ui/DialogWindow.qml`, after MuseScore 4's (MS1, docs/research/musescore-shell.md §4 and §7 DG1): a top-level window of its own, transient for the window it was opened from (the main window, a floating panel, the Style manager) and closed with it. Its title bar is SH1's style in one 32-pixel row on `panel` (`DialogTitleBar.qml`): the title (the command that opens the dialog) 12 from the leading edge, elided before the buttons, and at the trailing edge Close and, only while the dialog can be resized, Maximise (Restore while maximised), 46 × 32 with SH1's hover and press, Close's too; no Minimise and no application icon. While the dialog is not active the title and glyphs take `disabled`; in the high-contrast themes a 1-pixel `line` parts the row from the body. The frame is SH1's (`DialogFrame`, window_frame.h): on Windows the native one, which drops the minimise box and, on a fixed-size dialog, the sizing frame and maximise box, so Aero Snap and the system menu leave it its size; on Wayland and X11 frameless with the 1-pixel `line` boundary, and the resize band only on a resizable dialog. With "Use system title bar" the window system's frame stays and no row is drawn. The body sits 24 inside the window's sides (12 under the drawn row, 24 under the system's) on `panel`; the footer, 24 below it and 24 from the edges, holds extra actions at the leading edge and the closing buttons at the trailing one in the platform's order (WindowFooter), 8 apart, the default button in the accent. A fixed-size dialog is its content's size; a resizable one starts there and can only grow. The first open is centred on the opener, 20 lower, kept 20 inside the screen's free area and shrunk to fit; later opens are where it was left and as big, per dialog (`workspace.dialogGeometry`, dialog_placement.h; a fixed-size dialog keeps its position only, a place off every screen falls back to the first rule, and on Wayland only the size is kept). Esc closes (a control that takes Esc takes it first); Enter presses the focused button, else the default one (a multiline field keeps its Enter); the keyboard starts on `initialFocus`, else the default button with its ring, and goes back to the opener's control when the dialog closes. Modality is the dialog's: modeless by default (opening a shown dialog again raises it), or modal to its opener alone for a question that blocks an operation. About, Credits and the update offers are modeless. A wait the dialog cannot end (PU7's Install update, while the installer runs) is not closable: no Close on the drawn title bar, and Esc and the window system's close do nothing. A task of steps (PU7's Import legacy settings) is a wizard in one dialog: a stepper under the title bar (the current step in the accent, those done ticked), Back at the footer's leading edge and the step's action at its trailing one, the default.

**Popups (PK1, [#301](https://github.com/altqx/hikari/issues/301)).** Four kinds, each for one job; nothing new is drawn as an in-window Controls `Dialog` or a `MessageDialog` (shell_tests popupsAreOnTheKit holds the ones left, tests/ui/in_window_popups.txt, until the PU cards move them):
- **Window**: a dialog on DG1's frame (above), for a task with its own content.
- **Message box** (`MessageBox.qml`): a question, or a notice that needs an answer (an error that stopped an action, a choice that can lose data); modal to the window it came from. The title names the command (never "Prompt", "Confirmation" or "Info"); a severity icon (information, the warning triangle, the error octagon; a question takes the severity of what it leads to, never a "?"), one main line, an optional detail, the technical text under a Details disclosure with a copy button, and "Don't ask again" where the question can be hidden (Settings → Notices → Ask again brings them back). The buttons are named for what they do; the safe default is filled in the accent, a destructive one outlined in `danger` (`DangerButton.qml`) and never the default.
- **Popover** (`Popover.qml`, ColourPopover's surface `PopoverBackground.qml`): edits a value in place, under the control that opened it (above it without room below; in a window of its own when the host window is too small). Enter, a press outside or the control again keeps the change; Esc puts the value back. Small forms follow one rule: a popover when opened from a control on screen, a compact window when opened from a menu or a hotkey (the hotkey capture and the list chooser are both).
- **Notice**: a toast (`ToastStack.qml`) for what needs no answer, at the window's bottom right, the newest on top, three at most (a fourth drops the oldest information toast, or folds the oldest warning into "N more notices", which opens the Log); information fades after 5 seconds unless the pointer is on it, warnings and errors stay until ×; every notice goes to the Log too, and with Settings → Notices → "Show notices as toasts" off only there. An inline bar (`InlineBar.qml`) for a state that lasts and has its own actions (the update-ready bar), under the menus; it never takes the keyboard.

The forms built on them: the clash review (PK1-clash-review), Choose styles (PK1-choose-styles-live), the hotkey capture (PK1-hotkey-capture), the list chooser (PK1-list-chooser) and the date picker (PK1-date-picker).

File and session popups (PU1, [#303](https://github.com/altqx/hikari/issues/303)): a state that belongs to one Document is an inline bar under the Document tabs, shown only while that Document is the editing target (a file changed on disk, each file a restore could not find, an MKV being read); the startup offer is a card on the Home page, or the same offer as a bar when files were opened from the command line, and never holds the start back. A question about several Documents (unsaved work) is a window with a row per Document; about one, a message box. The file pickers are the native ones, titled for what they do or the file they are for ("Save “name” as"), each kind starting where it was last left.
**Notices and the Log (NT1, [#302](https://github.com/altqx/hikari/issues/302)).** Which kind a notice takes: one that reports an outcome, or a failure the user can read later (nothing was changed, the file did not open), is a toast, errors included; one that refuses what was just asked inside a window, or an error that stopped a command the user waits on (a script that did not load), is a message box with OK, modal to that window. The PU cards follow the same split; docs/ux/notices-inventory.md lists every notice and its kind. The calls, and nothing else:
- `notices.post(severity, title, text, {details, actions})` in QML: a toast and its Log entry. `severity` is `"info"`, `"warning"` or `"error"`; Main's stack is `root.notices`, handed to a component as its `notices: ToastStack` property; `post` returns the toast's id (0 when none shows).
- `LogController::notice(severity, title, text, details)` in C++ (any thread): the same, through the Log, which Main's stack shows (those given before the window is made, a profile's retired hotkeys, show when it is: the last ten); `LogController::log(text, severity, title)` puts a line in the Log only (legacy's silent log; an error with a title when a message box says it).
- `messages.ask(options, done)`: a message box (PK1's `ask` options; `done(id)` also on Esc). Each window that asks keeps its own `MessageHost { id: messages }`, which makes the box at the first question and queues the next; Main's is `root.messages`.

The title names the command that gave the notice (Open subtitles, Save, Find), never "Warning", "Info" or "Error"; the text is legacy's message on one line, and a technical or long part (a list, a script's traceback, the file's name for a player that refused it) goes under Details. A notice's title, text and details show as plain text, never markup: they may quote a file (a lyrics excerpt). A toast's Details opens the Log at its entry (out of fullscreen first). Toasts show above an open in-window dialog, modal or not, so a dialog's own warnings are seen while it is open.

The Log is a panel ("Log", `LogPanel.qml`, `LogController`), along the bottom under the other panels and the whole width, closed by default; nothing opens it by itself. File → Log and View → Panels → Log show and hide it; a toast's Details and "N more notices" → "Open the Log" open it (Details at its entry, marked with `select` and a 2-pixel `accent` bar, shown whatever the filters). Its strip holds three severity toggles with their counts (information, warnings, errors), a filter field that matches the title, text and details (Esc clears it) and Copy, which copies the entries shown; Ctrl+C copies the current entry. Each entry is one row: the time ("HH:MM:SS", `muted`), the severity icon, the title in bold and the text, selectable, with the details below in `muted`. The panel header names it; it has no heading of its own.

The Spellchecker is a panel too (PU6, "Spellchecker", `SpellCheckerPanel.qml`), along the bottom, closed by default: a tool that walks the document while the editor and the Grid stay in reach is a panel, not a window. Showing it (Subtitles → Check spelling, View → Panels) starts at the active Line; a layout that shows it does not. Its options are its "⋯" items, its outcomes toasts, and with nothing to show it says why in one muted line with the one command that helps.

**A running task in the toast corner (AD3, [#312](https://github.com/altqx/hikari/issues/312)).** A long task the user started and may cancel (a macro run) shows as a pinned item at the bottom of the toast stack, under the toasts (`ToastStack`'s default slot, `AutomationProgress.qml`): a one-line notice (its name and a slim bar, busy until it knows the progress) as it starts, growing in place into a card (PK1's Notice kind) once it has run about a second or has something to show. The card has the task, the bar, its log folded or open, Cancel, and a danger-outlined Force stop only after the grace; when the task ends it says how in its title (the outcome's icon and colour: done in the accent, cancelled and problems in `warning`, failed in `danger`) and stays until × only when there is something to read. It is the task's control, not a notice, so it shows with "Show notices as toasts" off too. It never takes the keyboard by itself; F6 reaches it as a region and Esc gives the keyboard back without cancelling. A log line (`RunLogLine.qml`) is the script's plain text in the monospace font after its level's name (error and fatal in `danger`, warning in `warning`, the others muted) and, when times are on, its time since the start; the application's own lines carry an icon in the level's place. The panel that keeps the runs uses the Log panel's filter field and a level threshold in one combo box, which fits a narrow panel where a toggle per level does not.

`success` in Light is legacy's fixed green (4.21:1, below 4.5:1 on its darkest surface). ## Keyboard, focus and tabs

The accepted navigation direction provides a route into every workspace region and keeps focus visible. HikariSub owns its native realization; HTML event handlers are not the implementation contract.

* **F6 / Shift+F6:** cycle forward/backward through the visible workspace regions. In the revised default D arrangement the order is preview, audio, editor, grid. Start from the currently focused region and maintain a meaningful order when layout or visibility changes. The revised study follows actual focus; native Qt must implement the same explicit navigation responsibility.
* **Tab / Shift+Tab:** navigate controls within their normal scope. A focused region must provide a useful next entry into its controls. Keep the focus ring visible at panel edges and in scrolled content.
* **Grid:** provide a clear keyboard entry and visible focus, retained selection when filtering hides a row, and an explicit empty state. The [painted-grid contract](subtitle-grid.md) governs native displayed-order navigation and the distinct selected set, current line and keyboard focus. The HTML study has a single-selection example in which Enter selects its focused row and enters the editor; this is illustrative, not an accepted production activation rule. Define activation and its effects on multi-selection in the native follow-up rather than copying the twelve-row HTML array.
* **Text inputs:** cursor movement, selection, IME composition and field-specific keys take precedence over surrounding navigation. The study's global Left/Right A–D comparison shortcut is harness-only and must not become an application shortcut.
* **Document tabs:** click selects the editing target. Left/Right navigate and activate neighboring tabs; Home/End select the first/last. The study wraps its two tabs. Use one active tab entry in the tab sequence, retain visible focus, and name the associated content. Tab activation changes document context, not interface appearance. Closing, reordering, overflow, protected-reference placement and dirty-document prompts need their document/workspace contracts; the gallery does not demonstrate them.
* **Menus:** opening the example menu enters its first item; Escape dismisses it and restores focus to its opener. Use complete native menu navigation rather than copying the sample's incomplete menu key handling.
* **Dialogs:** a modal operation contains focus, has an explicit title and cancellation path, and returns focus sensibly on dismissal. Cancel must not apply its pending edit. The HTML relies on browser dialog behavior; verify focus containment, Escape and restoration in Qt.

Focus is a ring in the text colour (Hikari theme layer, "Keyboard focus"), distinct from selection (the accent) and error (`danger`). Do not reduce focus to a subtle text-color change. Confirm that status updates can be announced without stealing focus or flooding assistive technology during typing.

## Icons, content and adaptive layout

The H mark, Unicode transport symbols, arrows, checkmarks and other glyphs are placeholders. They neither select a third-party icon pack nor establish redistribution rights for brand assets. Implement a coherent vector-icon set with consistent optical size, stroke weight and alignment. Record provenance and licence for any adopted assets; an icon-only action needs an accessible name and appropriate tooltip. Use directional mirroring where it conveys navigation, while retaining the meaning of media controls and data symbols. Font glyph availability must not decide whether an essential action is understandable. The set is specified in [icons.md](icons.md) (K1: drawn in house, UI icons only, following the appearance live in the theme layer's colours, K2).

The study stacks preview, editor, audio and grid below a 900-unit width and simplifies some content below 590. Those browser breakpoints and fixed stacked heights are exploratory references, not supported minimum-window sizes. In particular, hiding the layer field or an action at a narrow width is not permission to make that capability unreachable. Use resizing, overflow, scrolling and appropriate panel arrangements while preserving access to fields and commands. Check long translations, larger system text and mixed-direction text rather than assuming English widths.

The fields are one four-column grid of even columns: Name across; Family over three columns and Size; Font catalog over two, Emphasis (four toggles in one outline) and Text encoding; the four colours, each a swatch with its hex and a 46-wide transparency; Border, Shadow, Scale X, Scale Y; Angle, Spacing, Border type and the 3 × 3 Alignment grid over two rows; the three margins. A field where the selected Styles differ reads "Multiple values" in muted italic (a colour hatched). The name's problem is a `danger` line under it and a `danger` border; the rename check box sits there too. On a 1280 × 800 screen at 150 % (853 × 533) every control stays whole: the lists share the height and scroll, and the form scrolls under its pinned preview with its bar shown, sideways only on a smaller screen.

**Menus.** Every menu item keeps a check gutter and an icon gutter, so labels line up whether or not an item has an icon or a check, and shows its key binding right-aligned in the muted colour, in one notation ("Ctrl+Shift+O"): the menu bar's from the Global bindings, the context menus' from legacy's tab-separated text.

Dock chrome (headers, tab bars) follows MuseScore 4 under D3 ([#207](https://github.com/altqx/hikari/issues/207), [musescore-docking.md](../research/musescore-docking.md), [docking.md](../docking.md#chrome)) and is not redesigned by these rules. Its "⋯" button (K1's panel-menu, three dots) is the one menu icon in a header; the panel's name is its tooltip and accessible name ("<panel> options"). A panel reports the smallest size its content takes unclipped, and the docking engine keeps it at least that big; a row too wide for a narrow panel wraps (the Line inspector's fields) rather than be cut off.

## Qt Quick responsibilities and remaining verification

| Owner | Responsibility |
| --- | --- |
| Hikari theme and metrics layer | Expose the semantic palette, typography roles, spacing and radii once; resolve appearance and system/user scaling; keep subtitle-rendering styles separate. The palette half is K2's theme layer (`src/ui/theme.h`, above); typography, spacing and radii are not in it yet. |
| Shared Qt Quick Controls styling | Apply tokens to ordinary buttons, fields, selectors, toggles, sliders, menus, dialogs and tabs, including overlapping states and accessible labels/values. Avoid divergent per-screen colors. |
| Workspace and action layer | Own region order, focus restoration, shortcut scope, editing-target indication and modal command routing. Styling must not infer the editing target from the focused panel. |
| Grid model and presentation | Keep stable row identity, selection and editing state independent of delegates; render compact columns, current/selected/focused states and filtered-selection feedback. |
| Media surfaces | Present actual video, subtitle overlays, waveform and time state through their adapters. UI palette changes must not alter document rendering. |

These responsibilities implement the [architecture contract](../architecture.md); they do not select a docking dependency or a third-party component library. Figma remains on Starter for occasional handoff. Agent-built QML/HTML prototype tickets remain the mechanism for exploring unresolved interactions; acceptance of D is already recorded.

The HTML approval establishes visual direction and the demonstrated interaction vocabulary. It does **not** establish that the native application has passed any of the following:

* Native rendering and text readability in all four themes, including combined states and operating-system contrast behavior (the role contrast is measured above).
* System font changes, fallback/shaping, IME input, mixed-direction content, text enlargement, high-DPI scaling and movement between monitors with different scales.
* Complete keyboard reachability, visible focus, tab/menu/dialog semantics, screen-reader names/roles/values and announcements on the supported platforms.
* Large-document grid behavior, latency, memory, scrolling or frame-time targets; real audio/video synchronization and rendering performance.
* Production persistence, undo, docking, window restoration or the full document/tab lifecycle.

Those are implementation and verification obligations, not reasons to reopen the approved visual direction. Native findings should produce specific fixes or focused prototype evidence while preserving the accepted Compact Studio baseline.
