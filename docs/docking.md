# Native docking and workspace persistence

Accepted on 2026-09-27 by [altqx’s approval](https://github.com/altqx/hikari/issues/46#issuecomment-5853318062) of [Choose native docking and workspace persistence architecture](https://github.com/altqx/hikari/issues/46). This contract implements the already accepted [movable/floating workspace](ux/workspaces.md), one per Document tab since [ADR 0020](adr/0020-per-document-tab-layouts.md) (2026-10-18; the arrangement was shared by every tab before). [ADR 0017](adr/0017-owned-native-docking.md) records the engine and ownership choice. Native qualification remains required.

## Engine and dependency

Use **KDDockWidgets 2.4.1, QtQuick frontend only**, behind a Hikari-owned WorkspaceLayout service. Resolve the release to commit `c1d28d25ef5ba077915bcb2b6fa9e14df2a361f8`; pin the source digest, recipe and options in the accepted vcpkg/overlay graph before qualification. Use the [documented public entry points](https://docs.kdab.com/kddockwidgets-manual/latest/private_api.html): QtQuick DockWidget/MainWindow views plus Config, LayoutSaver and KDDockWidgets headers. Other Core headers are private; isolate and qualify any unavoidable private dependency inside the adapter. No Muse framework import or direct library access from document services.

The [upstream release](https://github.com/KDAB/KDDockWidgets/releases/tag/v2.4.1) supplies the candidate version. Its [QtQuick guide](https://github.com/KDAB/KDDockWidgets/blob/c1d28d25ef5ba077915bcb2b6fa9e14df2a361f8/README-QtQuick.md) documents the QtQuick-only option and cross-window effects caveat. Documented [engine features](https://github.com/KDAB/KDDockWidgets) cover nested splits, tab groups and floating groups. These match the accepted requirement more directly than implementing those mechanics over SplitView. A QWidget shell would alter the chosen Qt Quick shell boundary. A custom docking engine remains a fallback only after a concrete incompatibility, not an automatic scope expansion.

Use the dependency's [GPLv3 option](https://docs.kdab.com/kddockwidgets-manual/latest/licensing.html) with the repository's GPLv3 distribution; retain source, patches, applicable notices and license material in the release manifest. No commercial license purchase is assumed. Full payload/dependency compliance still belongs to the distribution gate.

## Hikari-owned identities and state

| Record | Responsibility |
| --- | --- |
| WorkspaceLayout | The service that shows one versioned arrangement at a time and keeps each Document tab's: dock tree/library payload, open panels, selected panel tabs, split ratios, floating groups and placement hints. It contains no subtitle content, undo history or media decoder. |
| WorkspaceArrangement | One Document tab's arrangement as a value apart from the engine: the built-in preset it started from and the engine's payload in Hikari's envelope (or the preset alone, built when the tab is shown). The Session stores it per tab; the `[Hikari]` section of ASS files (WS2) and saved layouts (WS3) store the same value. |
| PanelId | Stable untranslated role/instance identity, such as core Video/Audio/Editor/Grid or tool Styles/Search/Timing/History. Recreating a QML view never creates a second authoritative document. |
| Panel controller | Application-owned focus bookmark and tool binding, independent of dock view/window lifetime. Follow/pin and protected-reference checks use ordinary application contracts. |
| WindowId / affinity | One main editing window plus floating panel groups in the same workspace affinity. Floating groups cannot create another editing target. Fullscreen video is a separate presentation surface, not a dock group. |

The initial shell has one main window; multiple floating groups are allowed. No new independent multi-main-window document model is implied. Core panels and persistent tools may split, tab, float, close and reopen; closing a panel hides its presentation, never closes its Document or discards its draft. Closing a floating group hides its member panels and returns focus to the most recent visible region. View → Panels can restore each panel at its last valid placement, otherwise its default location.

Controllers and application state survive view reconstruction. Moving Video between QQuickWindows explicitly releases/recreates window-bound scene-graph resources with generation checks; CPU media context survives. Never share one QSG node/texture handle blindly between windows. Rearrangement cannot commit a text draft, retarget a pinned tool, mutate a protected reference or switch the transport owner.

## Keyboard and focus contract

Every panel exposes named actions for Show, Focus, Hide, Float, Dock, Tab with…, Move before/after and Resize. A keyboard placement dialog selects a destination panel/group and side; it must express every supported drag placement. Split resizing exposes numeric/step controls. F6/Shift+F6 traverse visible regions, including floating groups, while named focus commands provide direct access. Panel tabs expose names, selection and close/float actions to assistive technology (since D3 through each header's named "⋯" button and its menu, see [Chrome](#chrome)).

Capture a logical focus bookmark before moving/hiding. Restore the same control or a documented panel entry point after recreation; if it no longer exists, focus the next visible region. Focus never determines the editing Document. Modal task dialogs stay associated with their application task and logical owner even when a panel moves. Native cross-window activation, keyboard placement and screen-reader speech are validation requirements, not library guarantees.

**Focus follows the pointer** (the owner's decision, [#525](https://github.com/altqx/hikari/issues/525)). With Settings > Audio > "Focus the panel under the pointer" (`audio.autoFocus`, on by default), the pointer entering a panel, docked or floating, focuses it as a click would: the corner mark moves, its hotkeys work and Help opens its guide (`KeyRouter::focusRequested`). The focus stays where it is while a mouse button is held, a popup, menu or modal window is open, a key is being recorded, the application is not active, a control reached with the keyboard holds it, or a text field the user clicked, tabbed into or typed in holds it; the focus moves again on a click elsewhere. Off, a panel takes the focus on a click, and hotkeys still go to the focused panel.

## Save, restore and recovery

Use Hikari's schema envelope around the library's JSON layout: schema version, application/panel-registry version, exact engine version, preset/custom identity, engine payload and placement hints in device-independent units. Store tool bindings/session references separately so layout failure cannot corrupt them. Built-in Editing/Timing/Translation/Typesetting presets are immutable templates; automatic saving updates the current custom arrangement, and Reset layout returns to the chosen template without changing content or preferences. Presets, saved layouts, Reset this layout and Restore the previous layout change the current Document tab only.

**Saved layouts (WS3, #217).** The user's saved layouts replace legacy's View arrangements (WS3-view-arrangements-retired). Save layout as… keeps the current tab's arrangement under a name, in `layouts.json` beside `layout.json`: `{"schema": 1, "layouts": [{"name": …, "arrangement": <envelope>}]}`, written atomically, each arrangement the same envelope as a tab's, with a `layout` field naming the saved layout it came from. Saved layouts are global and are snapshots: applying one restores it in place in the current tab, and a later change to the tab does not change the saved layout. Reset this layout returns the tab to the saved layout it came from (or to its preset once that layout is gone). Rename and delete follow the tabs whose arrangement came from the layout; a deleted layout's tabs keep their arrangement under its preset. An entry that does not validate is listed disabled with the reason and written back as read; a file that cannot be read is kept as `layouts.json.unrestored` with a notice and no saved layout is listed. View > Layout and the layout switcher (in the title bar after the menus since SH1, #220) list the presets, the saved layouts and the three commands.

Persist completed layout operations atomically, not every drag pixel: use `serializeLayout()` plus Hikari's atomic writer, not upstream `saveToFile()`, which writes directly to an output stream. Retain the previous valid layout. At startup validate size/schema/IDs before invoking the engine (WS2: also no more windows, groups, layout items or placeholders than Hikari's panels can fill, each panel once, a floating window and a docked panel's place only in Hikari's one main window, a floating place only in one of the file's floating windows, and each panel's tab and place index a whole number from -1 that an int holds, each window's place and where a closed panel floats again within what a window can have, so moving them from the main window stays an int, since the engine makes one for each entry, indexes or looks up main windows unchecked and inserts a panel docked again at its tab index unchecked, and a layout tree whose every value has the type the engine reads and whose groups and items match one to one, since it reads the tree outside its own catch), construct known panels or its lazy factory, restore, then reconcile new/missing panels. The [LayoutSaver interface](https://github.com/KDAB/KDDockWidgets/blob/c1d28d25ef5ba077915bcb2b6fa9e14df2a361f8/src/LayoutSaver.h) exposes serialization, restore success and restored docks; Hikari owns compatibility validation and recovery. Unknown/newer data is preserved for diagnosis, not overwritten on a failed restore. A corrupt/incompatible layout falls back to Editing with an inspectable recovery notice and a restore-backup option. Suspend autosaving throughout restore and fallback: a false return can follow mutation of live dock views, so rebuild a known layout from surviving controllers after partial failure rather than treating the result as transactional rollback. These requirements follow the [pinned implementation](https://github.com/KDAB/KDDockWidgets/blob/c1d28d25ef5ba077915bcb2b6fa9e14df2a361f8/src/LayoutSaver.cpp#L368). At quit the saved layout is the one the window showed: KDDockWidgets' QtQuick main window filters its window's `QEvent::Close` and closes every panel before the window's own closing handler runs, so the shell's close guard (`Docking.guardClose`, filtering ahead of it) holds a close the review keeps back, and for a close that goes ahead makes the session's last save (`WorkspaceLayout.saveForQuit`); nothing saves the window being taken down after it.

**Per Document tab (ADR 0020).** The engine shows the current tab's arrangement; every other tab's is kept as its WorkspaceArrangement. When the editing target's tab changes, the tab left keeps the arrangement shown, and the tab shown gets its own back through the same restore as above but in place (`RestoreOption_RelativeToMainWindow` with absolute floating windows): the main window keeps its geometry, floating panels take their saved size and place where the platform allows, and the engine takes the panels out and puts them back without a frame drawn between. An arrangement equal to the one shown is not restored at all, so tabs with the same arrangement switch without touching the panels. A tab takes its first arrangement when it opens, shown or in the background: the Translation preset when its Document has `TLMode: Yes`, otherwise a copy of the arrangement shown then. A file opened into the tab counts as opening it for the Translation rule; otherwise the tab keeps its arrangement. After a swap the shell puts the Reference tray as the comparison has it (shown with the Grid while there is a reference). NT1: the Log ([#302](https://github.com/altqx/hikari/issues/302)) is a panel like the tools, closed in every preset, along the bottom the whole width when it opens in an arrangement that never had it. PU6: the Spellchecker ([#308](https://github.com/altqx/hikari/issues/308)) too, along the bottom under the other panels when it opens in an arrangement that never had it; a restore that shows it does not start a check. TM1: it puts the Original text panel as the editing target's Translation mode has it, shown while the mode is on (where the arrangement keeps its place, above the Line editor in one that never had it) and closed while it is off. Before the shell's first arrangement only the values change; once the saved layout file is restored, the current tab's own arrangement (from the Session or the Translation rule) replaces it, and a tab with none takes it. The layout file keeps the arrangement shown last, so a start without a Session opens as the last tab looked; the arrangement of the tab shown when the main window's close went ahead is the one the closing Session names.

The Session writes each tab's arrangement on a `Layout:` line in its compact envelope (WS1-session-layout). A line that fails validation gives that tab the Editing preset, and a restore that fails, also in part, rebuilds the default arrangement for the tab shown; either way the notice names the tab (or "this tab") and why, and the rejected text is kept in `layout.json.tab.unrestored`. A Session without the lines (legacy's, or one written before WS1) restores each tab as a new one.

An ASS or SSA file keeps its tab's arrangement too, in a `[Hikari]` section (WS2-hikari-section, [WS2 #216](https://github.com/altqx/hikari/issues/216)): `Layout=` and the compact envelope in base64 (`WorkspaceArrangement::serialiseForFile`), with the preset and the saved layout the arrangement started from (WS3): opened where a saved layout has that name, the tab starts from it (Reset this layout returns to it); elsewhere, from the preset. The file's copy has no screen positions: the screens, each window's screen and the main window's position are left out, the main window's size stays so the docked panels keep their proportions, and floating windows (and the places closed panels float again at) are kept from the main window's top-left. Opening the file places them from the main window as it is then (`parseFromFile`) and restores in place as any tab change does. A save or an autosave writes the tab's arrangement (an autosave into its recovery file only: the open Document keeps its file's section, so a save with the setting off writes no other); opening gives the tab the file's (so does recovering an autosave or opening a legacy autosave; a Matroska track has none, as Demux keeps only its Script Info, Styles and Lines), the Session's `Layout:` line taking precedence when a Session is restored (a Session tab without one takes the file's, also when its missing file is retried or relinked); a value that does not validate is named in the log and the tab starts as a new one. "Save panel layout in subtitle files" off, files are neither read nor written for it. Other formats keep the arrangement only in the Session.

After every restore the shell fits each floating window's layout to its layout area again (`fitFloatingLayouts`). The pinned engine rebuilds a floating window's layout at its area's size while the window's own title bar still shows (it has no groups yet), hides that title bar once the layout has its lone group, and ignores the area's resizes while the restore runs ([`Layout::onResize`](https://github.com/KDAB/KDDockWidgets/blob/c1d28d25ef5ba077915bcb2b6fa9e14df2a361f8/src/core/Layout.cpp#L320)), so the layout stays a header's height (35 px) short of its area. On X11 and the offscreen platform the window's restored size reaches its contents after the restore and the layout follows it; a Wayland window has its size at once and nothing follows, so the floating panel came back 35 px short above an empty band (D1 native gate on sway, KWin and mutter, 2026-10-13).

On Windows/X11, intersect saved placement with available screens, constrain minimum sizes and keep title bars reachable; removed monitors return floating groups to the main screen, whole and at their size in device-independent pixels (see [Chrome](#chrome)). Use screen identity and geometry as hints, not durable hardware identity. On Wayland, retain grouping and size where supported but let the compositor place windows: [upstream documents separate move/dock title bars and unavailable absolute position restore](https://docs.kdab.com/kddockwidgets-manual/latest/qpa-wayland.html). Since D3 the floating windows are borderless everywhere, so the header itself moves its window through the compositor there (see [Chrome](#chrome)). Do not promise coordinate-identical restoration across platforms.

On every platform the main window is never smaller than its docked layout's minimum (the user's decision 63, 2026-10-16), so no docked panel is cut off past the window's right or bottom edge. The engine resizes only a main window that is its window's root item, and the DockingArea sits in an ApplicationWindow under its menu bar, so `Docking.followLayoutMinimum` (called by `Main.qml` for the Classic area) sets the window's minimum to the layout's minimum (`Layout::layoutMinimumSize`: the docked panels' minimums, their headers and the separators) plus the window's rows outside the docking area, within the screen's available area. It follows every change the layout reports (a panel docked, floated, shown or hidden, a panel's own minimum changed) once the layout has been still for 100 ms and no layout restore is running, so the window does not grow to the larger minimums a Reset layout or a restore passes through; a window made smaller by a program or a restored geometry grows back to it. Floating windows keep their own minimum ([Chrome](#chrome)).

## Chrome

[D3](https://github.com/altqx/hikari/issues/207) gives the dock chrome MuseScore 4's form (user decision 2026-10-05; [research at v4.7.5](research/musescore-docking.md)). MuseScore's code is for its KDDockWidgets 1.x fork, so the design carries over and the code does not: the adapter (`src/ui/docking.cpp`) configures the 2.4.1 engine and supplies its views (`DockTabBar.qml`, `DockTitleBar.qml`, `DockGroup.qml`, `DockSeparator.qml`, `DockFloatingWindow.qml`, `DockDropHighlight.qml`, `DockMenuButton.qml`). Colours come from the theme layer's roles and menus are `ShellMenu`s; the look is specified in [visual-language.md](ux/visual-language.md) (Composition, sizes, Keyboard focus).

**One header row per group.** The engine always shows a group's tabs and hides its title bar (`Flag_AlwaysShowTabs`, `Flag_HideTitleBarWhenTabsVisible`), so `DockTabBar.qml` is every group's header, docked or floating, and draws it in one of two modes:

- a lone panel: a title bar, its title in bold and a "⋯" button;
- two or more panels, or a horizontal panel even alone (the Grid, the Reference tray, Search, the Original text panel, the Log and the Spellchecker: `Docking.setPanelHeader`): a tab bar only, the "⋯" button on the selected tab, and the current panel's toolbar in a slot right of the tabs (the Reference tray's navigation lives there instead of in a row of its own: Follow the editing line, the match status, Show nearest line, Previous and Next match; no close button; the Original text panel's translation buttons and toggles, TM1).

The "⋯" button draws K1's `panel-menu` (three dots), not `menu-more`, the double chevron the Line editor's Manage tag buttons used for a list that drops open (retired with that button by LE5). Tabs that do not fit keep the selected one at its width and share what is left in proportion, cut off under a 20-pixel fade to 70 % of the strip (MuseScore's overflow); they never scroll or wrap. The whole header shows the move cursor (`Qt::SizeAllCursor`), its buttons the arrow. The toolbar slot belongs to the current panel: its free part (the tray's status text) drags, double-clicks and right-clicks as the current tab does.

The engine's title bar (`DockTitleBar.qml`) shows only above a floating window that holds several groups: the window's title and a "⋯" menu that docks or closes the whole window. Panel content never repeats the header's title.

**The "⋯" menu.** There are no float or close buttons. The "⋯" button, a right click on the header, Space or Enter on the button, and the menu key or Shift+F10 on a tab ask for the panel's menu (`Docking.requestMenu`); `Main.qml` owns it (`panelOptionsMenu`). It lists the panel's own items, a separator, then Move panel… (the keyboard placement window), Move tab left and Move tab right (D1's Move before/after, only for a panel in a group of tabs: its tab one place along the bar, off at the bar's end, mirrored in a right-to-left layout; the panel stays the shown tab and keeps the focus, and the order is saved with the layout; `Docking.moveTab` moves it in the engine's tab list and in the tab bar's model, as the pinned QtQuick frontend's `TabBar::moveTabTo` is a stub and reinserting a panel into its own group takes it out), Undock (Dock while the panel floats) and Close. Own items are settings with no place in the panel's body or its header's toolbar, never a copy of a control the header already shows; no panel has any yet. The Reference tray's Close reads Close reference and closes the reference, the tray with it (legacy's close mark, `DestroyPreview`), so the tray's header has one close, in this menu. An item the panel cannot do is disabled: Close for a dock that is not closable, Move panel… and Dock for one that is not dockable (every Hikari panel can close and undock today). A double-click on a header floats its panel (the tab under the pointer in a group) and, on a floating panel's header, docks it again. In a floating panel the menu opens in the panel's own window, inside its frame (the floating window re-places Qt Quick's popup overlay when its size changes: the engine sizes the window's content before the window, and the overlay otherwise keeps the offset of the window's first size; found by the native gate). View > Panels keeps its Show, Hide, Float and Dock per panel.

**Keyboard and names.** F6/Shift+F6 move between panels, and from a header to the panel after its own. The header is in the Tab order once: Shift+Tab from a panel's first control reaches its selected tab (a title bar's "⋯" button); Right goes from the selected tab to its "⋯" button, Left back, and Left/Right on the tabs select the neighbouring panel. The header's keys come before the shell's shortcuts (Left and Right otherwise step frames). A title bar is a title bar named after its panel; a tab bar is a page tab list of page tabs named after their panels, checked when selected, pressed to select; the button is a button named "<panel> options" (MuseScore's is a bare "Menu").

**Separators and drop feedback.** Separators are 1 pixel (`Config::setSeparatorThickness(1)`) in `line`, with a hit area 5 pixels wider on each side. While a panel is dragged, the accent highlight (1-pixel border, 30 % fill) covers the area the drop would take: the half of the group under the pointer for a side, the whole group for a tab (over its header or its middle third), a strip along the window's edge within 24 pixels of it. Anywhere else, or where the engine does not allow a drop, nothing is highlighted and the panel stays floating. A drop beside or into the group the dragged panels would leave empty is not allowed (`dropKeepsItsGroup`): on Wayland the engine floats them only at the drop, after emptying that group, and docking them against it lost them ([#524](https://github.com/altqx/hikari/issues/524)). The engine's built-in Segmented indicators cannot be styled to this: at 2.4.1 the QtQuick view factory has no view for them (`createSegmentedDropIndicatorOverlayView` returns none, and the overlay needs one), and their model is a set of fixed-girth wedges drawn as the hot zones, not a highlight of the drop's area. So the Classic overlay stays and its two parts are Hikari's: its indicator "window" (`DropZones`) draws nothing and finds the drop from the pointer's position, and its rubber band is `DockDropHighlight.qml`, which the engine sizes to the drop's area (`DropArea::rectForDrop`). The dragged window is drawn at 70 % opacity where the window system composites, so the highlight under it shows.

**Floating panels.** A floating panel is a tool window (`Qt::Tool`) owned by the main window, with the same header, on every platform borderless (`Qt::FramelessWindowHint`) and transparent around its frame, with a drawn 8-pixel shadow, a 1-pixel `line` boundary and 3-pixel corners (`InternalFlag_UseTransparentFloatingWindow`; `Docking.floatingShadow`); its shadow's edges resize it through the window system (`QWindow::startSystemResize`). X11 without a compositing manager shows no transparency, so the margin would come out black: there (Qt's xcb integration says whether `_NET_WM_CM_S0` has an owner) the shadow is 0, the frame fills the window and a 4-pixel band inside its edge resizes it (`Docking.floatingShadow`, `Docking.resizeGrip`; found by the native gate). Windows is no exception: the engine's Aero-snap frame (`Flag_AeroSnapWithClientDecos`, its default), which kept the system's frame, shadow and snap, is off. On Wayland the frameless flag only stops Qt from asking for a server-side frame (it creates no xdg-decoration object), and a compositor may frame a window that asks nothing (sway with a border rule did, so the native gate saw the panel's name twice). The adapter therefore asks the compositor itself, before the window's first buffer: `zxdg_toplevel_decoration_v1.set_mode(client_side)` (`window_decorations.cpp`, the protocol through Qt's `QWaylandClientExtensionTemplate`; mutter has no xdg-decoration and frames nothing anyway). sway and KWin honour it for floating windows. Where a compositor answers `server_side` all the same, it frames the window, and the panel draws no shadow inside that frame: the frame fills the window and the 4-pixel band inside its edge resizes it, as on X11 without a compositing manager (`Docking.windowSystemFrame`, `Docking.windowShadow`; the Hyprland native gate found Hyprland's border going round the shadow's transparent margin, 8 pixels off the panel's frame). Most such frames have a title bar (sway's `border normal` on the window, KWin's), which names the window, so a lone panel's header whose title is the window's drops its title and keeps its "⋯" button, and a floating window of several groups drops its title bar's title; tabs stay (`Docking.windowSystemTitle`). Hyprland answers `server_side` to every window but draws only its border, no title bar, so there the header keeps the panel's name. xdg-decoration does not say which kind of frame a compositor draws, so the adapter tells Hyprland by the globals it advertises (`hyprland_*`, read once on a registry and queue of its own); any other compositor's server-side frame counts as one with a title bar.

Moving splits the header on Wayland and X11 (the user's choice, 2026-10-12, [#207](https://github.com/altqx/hikari/issues/207)); on Windows the whole header is the engine's drag (the owner's choice, 2026-10-15: Windows' Snap never takes the borderless tool window during the free part's move (the Winix VM and real hardware, 2026-10-15), so the split offered nothing there, and the owner's first drag to dock on real hardware started right of the title, moved the window and did not dock). Where it splits: A floating window's title (a title bar's bold title, a tab bar's tabs) is the engine's drag: it moves the window, shows the drop highlight and docks (on X11 and Windows the engine moves the window itself; on Wayland, where it cannot place windows, the drag is a drag-and-drop). The rest of the header (right of the title, up to the "⋯" button; right of the tabs, up to the toolbar) moves the window through the window system (`QWindow::startSystemMove`, `Docking.startSystemMove`, `DockSystemMoveArea.qml`), so the window system's own move applies there: an X11 window manager's or a Wayland compositor's edge tiling, where they take a borderless tool window. A system move hands the pointer to the window system for the rest of the drag, so that part does not dock; it starts only once the pointer has moved, so a click there hands nothing over and a double-click there still docks the panel. The title ends where the free part starts, elided if it must be; short of room, a long title gives way to keep the free part 48 pixels wide, but keeps 48 itself; the rule is the same at every scale, since the header is laid out in device-independent pixels (the 125–200 % runs of `docking_qualification_tests`). Where the platform declines the system move (an X server whose window manager does not move windows through `_NET_WM_MOVERESIZE`, or none, as under `xvfb-run`), the window follows the pointer itself. The title bar of a floating window of several groups (`DockTitleBar.qml`) is split the same way. A floating panel also docks by a double-click on its header, its menu's Dock or Move panel…. Windows and the offscreen and minimal platforms keep the engine's drag over the whole header (`Docking.platformUsesSystemMove`): there a press anywhere on the header but its "⋯" button and a toolbar's buttons drags with the drop highlight and docks, a double-click docks and a right click opens the panel's menu (`docking_qualification_tests` wholeFloatingHeaderDocksWhereItDoesNotSplit); the tests split it offscreen with `Docking.setSystemMove`. A floating window keeps its size in device-independent pixels when its screen's scale changes: a live change of the display scale on Windows left the floating Line editor at its pixel size, 80 % of the panel at 125 %, with its content cut off, so once the change settles the window takes back its earlier size, at least its panels' minimum (`dockchrome::kScaleSettleMs`, `docking_qualification_tests` floatingPanelKeepsItsSizeAcrossAScaleChange, the Windows gate's `dpi` step). The same holds when it moves to a screen of another scale: outside Windows, Qt first resizes the window for the new screen's scale and only then updates its device pixel ratio, so that resize is not taken as the size to keep (the Linux CI's offscreen runs, 2026-10-15, kept a 600 × 220 panel moved onto a 150 % screen at 400 × 147). A floating window whose monitor goes away (unplugged, switched off, Windows' "PC screen only") comes back whole on the main window's screen, at its size in device-independent pixels from before the loss (at most that screen's available size), as close to where it was as fits: on real Windows hardware (2026-10-15, a panel on a 150 % monitor right of a 100 % one) the window system first moved it onto the remaining screen at its pixel size, the shell's screen check found that smaller window reachable, and the scale settle then gave it back its size where it stood, leaving only its left 173 pixels on the screen. The window is placed once the window system has stopped moving and resizing it, and again if the window system moves it within `dockchrome::kScreenLossWatchMs` of the loss; the engine's view is made to fill the window again, as after the run that left a window larger than its panel. Not on Wayland, where the compositor places windows (`docking_qualification_tests` floatingPanelComesBackWholeWhenItsScreenGoesAway, offscreen, removing a second screen at 150 %). The native gate re-proves, on each compositor and on X11 and Windows: move (on Wayland and X11 both header parts: the title's drag with the drop highlight, the free part's system move with the window system's snapping or tiling; on Windows the drag with the drop highlight from the title and from right of it), resize from the shadow, the drawn shadow (on X11 also without a compositor, where a transparent window may show black around the frame), focus and activation, drag-to-dock with the highlight, mixed DPI and monitor removal.

**Minimum sizes.** Each panel reports the smallest size its content takes unclipped (`Docking.setMinimumSize`, from the Panel's `minimumBodySize`), and the engine keeps its group at least that big plus the header, when separators are dragged and when a restored layout brings older sizes (`refreshDockConstraints`). Rows that would be cut off in a narrow panel wrap instead (the Line inspector's fields). Legacy's placement and proportions stay: the default arrangement first takes the panels' minimums, then gives the audio box its 170 pixels, growing the top row into the Grid's when the Line editor below has no room to give.

## Required native gate and review
