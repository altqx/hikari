# Distribution and update policy

**Decided by altqx on 2026-10-13; [ADR-0019](adr/0019-installers-and-seamless-updates.md) records it.** It replaces the policy of 2026-09-27 ([ADR-0012](adr/0012-distribution-and-updates.md): Inno Setup, notification-only updates, a signing gate for stable releases). HikariSub legacy (0.0.x, branch `legacy`) and HikariSub (0.1.0 and later, branch `main`) follow the same rules, so HikariSub can replace legacy in place.

## Packages

Every release publishes these assets, where `<V>` is the version without its `v`:

| Package kind | Asset | Installs to | Updates |
| --- | --- | --- | --- |
| Windows installer (NSIS, unsigned) | `HikariSub-<V>-windows-x64-setup.exe` | "Just me": `%LOCALAPPDATA%\Programs\HikariSub`, no administrator; "All users": `%ProgramFiles%\HikariSub` | In the app, silently |
| Windows portable | `HikariSub-<V>-windows-x64.zip` | Where it is extracted | Notice and release page |
| AppImage | `HikariSub-<V>-linux-x86_64.AppImage` | The file itself | In the app: it replaces itself |
| deb | `hikarisub-<V>-linux-amd64.deb` | `/opt/hikarisub`, `/usr/bin/hikarisub` | In the app, through `pkexec` |
| rpm | `hikarisub-<V>-linux-x86_64.rpm` | `/opt/hikarisub`, `/usr/bin/hikarisub` | In the app, through `pkexec` |
| Linux portable | `hikarisub-<V>-linux-x86_64.tar.gz` | Where it is extracted | Notice and release page |
| Arch Linux | AUR package `hikarisub-stable-bin` (stable releases) or `hikarisub-beta-bin` (every release), built from the tar.gz | `/opt/hikarisub`, `/usr/bin/hikarisub` | Notice: update with the package manager |

The release also carries `SHA256SUMS`, the AppImage's `.zsync` for external AppImage updaters, and `hikarisub-update.json`, the update manifest. Nothing is code-signed.

Each installed copy has `package-kind.txt` beside the executable: `nsis-user`, `nsis-machine`, `appimage`, `deb`, `rpm` or `arch`. No marker means a portable copy. About and `hikarisub --version` name the kind, so bug reports carry it.

HikariSub keeps its settings in the platform's user folders (`QStandardPaths`), whatever the kind. Removing or upgrading a package never deletes them, nor the update cache. The settings importer also looks in installed legacy's data folders, `%LOCALAPPDATA%\HikariSub\Legacy` and `~/.local/share/HikariSub/Legacy`.

## The Windows installer

- One installer, built with `makensis` 3.13 on Linux from the staged Windows payload, for both codebases. `packaging/windows/build-makensis.sh` builds it from the NSIS release's source and zip, pinned by SHA-256 in `tools.lock`: Ubuntu's `nsis` is 3.09, and NSIS before 3.11 has CVE-2025-43715 (a local user creates an elevated installer's plug-ins folder first and plants a DLL in it). Each branch has its own `packaging/windows/hikarisub.nsi`; the codebase's part is generated into `payload.nsh`.
- The user chooses **Just me** (the default; no administrator, `%LOCALAPPDATA%\Programs\HikariSub`, `HKCU`) or **All users** (one UAC prompt, `%ProgramFiles%\HikariSub`, `HKLM`). For that prompt setup starts its own file again elevated; it holds that file open with reads shared only from its start, and every folder above it with deletes not shared, so no other process can rename or replace the file, or rename a folder on the way, before UAC finds the path again; from a path through a junction or symbolic link, a network path, or without the holds, it says to run setup as administrator instead. An existing install fixes the choice; changing it means uninstalling first. An all-users install goes only to a new folder directly in Program Files, which takes Program Files' rights (or stays where the existing all-users install is): a folder elsewhere could have been made by a standard user, and one already in Program Files may be another program's with rights that let users change it, or hold a junction; either way the user could then replace the program every user starts. `/D=` anywhere else exits 2. A folder an uninstall left behind (it keeps files the user added) is not reused. The elevated relaunch and an all-users update do not read HKCU for a per-user install, since it is the HKCU of whichever administrator approved UAC.
- The program is `HikariSub.exe` in both codebases, so the Start menu shortcut, the App Paths key and the file associations stay valid when Qt replaces legacy. The Qt executable carries legacy's file-type icon resources with legacy's ids.
- `HikariSub.exe` is a small launcher without Qt (#584). It shows a still splash (the art in `src/app/windows/splash/` for the dark and light themes, the icon and name for the others) within about a second, then loads the app from `HikariSubApp.dll` in the same process and closes the splash once the main window has drawn its first frame. A cold start after a reboot otherwise shows nothing for 20–30 s while Windows reads and scans the unsigned payload. The launcher takes the colours from `%LOCALAPPDATA%\HikariSub\cache\startup-look.txt`, which the app rewrites when the theme changes; before the first run it follows the system's light or dark setting. No splash shows for `--version`, `--export-docs`, the update handoff, or while another HikariSub or an update's setup runs. The splash does not animate: on the 2-vCPU test VM, whose desktop composites in software, an animated progress bar delayed the main window by about 2 s. Linux has no launcher: it starts in 1–2 s, and a splash there would need its own Wayland or X11 client before Qt.
- Optional components: **Associate subtitle files** (on by default) registers `.ass .ssa .srt .sub` as an eligible handler and becomes the default only where no other app is; never `.txt`. **Desktop shortcut** is off by default.
- The payload ships the Qt runtime from `windeployqt` and the app-local MSVC runtime from the Visual Studio redistributable folder, never from System32. The installer runs no `VC_redist`, so a per-user install needs no administrator.
- An upgrade (legacy to legacy, legacy to Qt, Qt to Qt) installs over the previous files and removes the files of the previous payload that the new one lacks, using the `install-manifest.txt` each installer leaves. It never deletes a file it did not install. A downgrade asks first, and a silent downgrade is refused.
- Silent switches for the updater: `/S`, `/CURRENTUSER` or `/ALLUSERS`, `/UPDATE`, `/WAITPID=<pid>`, `/RELAUNCH`, `/D=<dir>`, with fixed exit codes. The installer waits for the running app to exit and never kills it. It finds a running app by the mutex `Global\io.github.altqx.HikariSub.Running`, which every window holds, the one that serves as the session's single instance (WS5: a mutex in the session's `Local\` namespace and a named pipe) or not; a start that hands its files to that instance exits at once.
- Uninstall removes the files, shortcuts, associations and registry keys it created, and never the user's settings, documents, recovery data or the update cache.
- An all-users uninstall started without administrator rights starts itself again through UAC only when the install folder is protected from the user, by the updater's rule (`packaging/windows/protected.nsh`, each right opened alone under the user's own token). Otherwise it says so and exits 4: in a folder the user can change, `package-kind.txt` and the uninstaller that would run elevated are the user's to rewrite.

## Update check

The check reads GitHub's release list, 50 releases to a page and four pages at most. It keeps the releases that are not drafts, have a `v` + SemVer tag, are newer than the running version and fit the channel ("Stable versions only" skips GitHub prereleases and SemVer prerelease tags on a stable build; a prerelease build always takes prereleases, as legacy does). It walks at most five of them, highest version first:

- A release with `hikarisub-update.json` has its manifest read (64 KiB at most). A manifest that does not arrive or breaks its rules skips the release. One with an unknown schema counts as no manifest.
- A release without a manifest (every release before this policy) takes its packages from the assets' GitHub digests, and is offered to the codebase its version names.
- A release whose manifest's `offer_to` does not name `qt` is skipped.

URLs are built from the tag and the asset name (`https://github.com/altqx/hikari/releases/download/v<V>/<asset>`), never taken from a reply. Downloads may be redirected only to `github.com`, `objects.githubusercontent.com` and `release-assets.githubusercontent.com` over https. The automatic check keeps legacy's schedule (a day after each check, "Remind me in a week").

What's new (SH3, [#223](https://github.com/altqx/hikari/issues/223)) reads the same release list, and only while "Check for updates automatically" is on: once per installed version, at the start after an update (sharing the start's own check when one is due; that read is no check and moves no schedule) or from Help > What's new while nothing is cached. It keeps the notes after the version run before up to the installed one in `whats-new-<copy>.json` in the update cache (4 MiB at most), named for the copy as the pending record is, and shows them from there offline or with checks turned off later. Past 4 MiB the lowest versions lose their notes first (those neither channel shows among its ten before the rest; they still count in "And N earlier versions"), then the lowest versions go. The same file keeps the version that ran last and the one its notes start after, so copies sharing the settings (a package and an AppImage) each keep their own; without it a start is a first one. The notes' images and links are never fetched.

What the first passing release offers depends on the package kind:

- **NSIS, AppImage, deb, rpm** with a package for the kind: the download. A package that needs a newer Windows (`min_os`) or glibc (`min_glibc`) than the system has is only named, with the requirement.
- **AUR:** "HikariSub `<V>` is available; you have `<old>`. You installed HikariSub from the AUR, so update it with your package manager or AUR helper, for example yay -Syu or paru -Syu." `aur-channel.txt` beside the executable names the package's channel: `hikarisub-beta-bin` ("beta") is told about prereleases and `hikarisub-stable-bin` ("stable") only about stable releases, whatever "Stable versions only" says, and the option is hidden for them. A prerelease that the install's package does not carry points at the AppImage instead, as that package carries stable versions only. Nothing is downloaded.
- **Portable**, or "Install updates automatically" off: the notice and the release page.

## Seamless update

"Install updates automatically" is on by default and shown only for the kinds that install. The automatic check then downloads without asking; the menu's check offers "Download and install", with a progress line in its place while it runs.

1. The package goes to `%LOCALAPPDATA%\HikariSub\Updates\<copy>\<V>\` or `${XDG_CACHE_HOME:-~/.cache}/HikariSub/Updates/<copy>/<V>/` (an AppImage's beside the AppImage, as `.<image name>.<V>.update`), as `<name>.part`. Its size and SHA-256 are checked as it arrives; a mismatch deletes it. `pending-<copy>.json` in the cache records it. The cache is the user's and shared by every copy they keep, so each copy has its own record and markers, named for the kind (`deb`, `nsis-machine`, ...) and, for an AppImage, a hash of its path. A copy never offers, installs or removes another copy's update, and clears only its own download folders.
2. A bar under the menus says "HikariSub `<V>` is ready to install", with What's new, **Restart now** and **Later**. It comes back at each start while the update waits.
3. Restart now runs the normal quit: the save review of every modified document, which can cancel it. Later installs at the next normal quit, without the restart; an AppImage at the start after that quit (below).
4. After the main window has closed, the file's size and hash are checked again, then it is handed off:
   - **NSIS:** the app starts its own installed `hikarisub.exe --hikari-apply-update <V> <file> <pid> <0|1>` and waits for it with a busy notice: elevated through UAC for "All users", unelevated for "Just me"; declining UAC keeps the update pending. `package-kind.txt` is no more protected than its folder, so UAC is asked only when the unelevated user can change nothing in the install folder or under it (no write, delete, `WRITE_DAC` or `WRITE_OWNER`, no reparse points) and can replace no folder on the way to it; otherwise the update is not installed automatically and the next start says to run the installer by hand. That process trusts nothing the user's side wrote, the pending record included. It checks that `<V>` is a release version newer than its own, downloads the release's `SHA256SUMS` itself over HTTPS from `https://github.com/altqx/hikari/releases/download/v<V>/SHA256SUMS` (following each redirect itself, only to GitHub's hosts, and taking a server's certificate only when it chains to a root in the local machine's stores: the user's own root store, which an unelevated process can add to, does not count), and, for "All users", copies the installer into a new folder under `%windir%\Temp` that only SYSTEM and administrators can write. It hashes the file through a handle that denies writes and renames and runs `setup.exe /S /UPDATE /WAITPID=<pid> [/RELAUNCH] /CURRENTUSER|/ALLUSERS /D=<install dir>` only when the digest is the one listed for `HikariSub-<V>-windows-x64-setup.exe`. A refused file is deleted with its pending update, and the app says why. The installer waits for the app and its mutex `Global\io.github.altqx.HikariSub.Running`, and restarts it unelevated. It holds `Global\io.github.altqx.HikariSub.Installing` from its start to its exit, and the handoff returns only once it does: an installed copy started meanwhile would hold its program open and stop the update, so it leaves at once and sets the installer's event `Global\io.github.altqx.HikariSub.StartAfterUpdate` (any signed-in user may set it: an all-users installer that another administrator approved runs in that account's profile), and the installer starts HikariSub as the desktop user when it is done, as with Restart now.
   - **AppImage:** the new image replaces `$APPIMAGE`, which stays as `$APPIMAGE.old`, and the old process waits up to 60 s for the new one to report its window (`--hikari-health=<file>`, named for the copy and the version), and otherwise puts the old image back and starts it. With Restart now that happens after the quit. An ordinary quit cannot watch the new image's first start, so it only writes `at-start-<copy>` in the update cache; the next start of the old image does the swap and the watch before anything else, passing on its files, and exits.
   - **deb, rpm:** "Installing update..." while `pkexec /opt/hikarisub/libexec/hikarisub-update-helper install <file> <version>` asks for the password. The helper takes no digest or package kind from its caller. It checks that the version is a release version newer than the installed package, copies the file into its root-owned `/var/cache/hikarisub-update`, downloads that release's `SHA256SUMS` itself with curl over HTTPS from the fixed GitHub URL, and installs the copy with apt, dnf or zypper only when its digest is the one listed for this kind's release file and its name, architecture and version are right. The packages depend on `curl` and `ca-certificates` for it. Restart now then starts `/usr/bin/hikarisub`. A dismissed prompt keeps the update pending; a refused package is deleted. Without `pkexec` or a polkit agent, the bar names the downloaded file, with Show in folder and Copy install command. The command is `sudo /opt/hikarisub/libexec/hikarisub-update-helper install <file> <version>`: the same helper and checks, run through sudo, which names the user in `SUDO_UID`. The package manager is never handed the user's own file, which another process of the user's could replace after the app's check.
5. A failed hand-off is told once at the next start (`last-result-<copy>.json`, which another copy never reads or removes; the installer writes `last-result-nsis-user.json` or `last-result-nsis-machine.json` for its scope). After Restart now, a hand-off that installed nothing (a changed download, an installer that could not start, an AppImage folder that became read-only) starts the version still installed, which says why. The next start of the new version deletes the update's leftovers.

No flow installs a version that is not newer than the running one.

## The user folder

Everything a user may edit or keep is in one user folder, Aegisub's `?user` ([UD1-user-folder](compatibility-decisions.md)):

| Copy | User folder | Caches (index files, audio cache) |
|---|---|---|
| Linux | `$XDG_CONFIG_HOME/hikarisub` (`~/.config/hikarisub`) | `$XDG_CACHE_HOME/hikarisub` (`~/.cache/hikarisub`) |
| Windows | `%APPDATA%\HikariSub` | `%LOCALAPPDATA%\HikariSub\cache` |
| Portable | `user` beside the program | as the platform's |

`HIKARISUB_USER_DIR` names another user folder (tests, power users). The folder holds the settings files and list files (below), `automation/autoload` and `automation/include` (DependencyControl's modules and its config too), `dictionaries` (Hunspell pairs, `UserDic.udic`), `catalogs` (style and font catalogs), `presets` (saved workspace layouts) and `recovery`. Help > Open user folder and Settings > General > Folders open it. No uninstaller deletes it.

**Settings files (CF1, #488).** The settings are three files, each starting with `version = 1` (`"version": 1` in JSON) and holding only values that differ from the default. The rule is: what you set on purpose goes in settings, and what the app remembers goes in state.
- **`settings.toml`** holds the preferences. A setting's dotted id is tables and a key (`audio.cacheFilesLimit` is `cacheFilesLimit` in `[audio]`), and lists are arrays. The tag buttons are `[[editor.tagButton]]` slots (`tag`, `type`, `name`, `icon`) after `editor.tagButtons`, the count shown. The script dialogs' presets are `[automation.dialogPresets]`, a table of arrays of tables keyed by dialog.
- **`hotkeys.toml`** holds the changes from the default shortcuts, one table per window: `[global]`, `[grid]`, `[editor]`, `[video]` and `[audio]`.
  - A key is the command's symbol, and a value is Qt's key text, so `GLOBAL_SAVE_SUBS = "Ctrl+Shift+S"` comes out with its name as a comment. `""` takes a default shortcut away.
  - A command has one shortcut per window, so an array uses its first entry only, and the Log names the rest as ignored.
  - `[automation]` holds the scripts' shortcuts: `"<legacy name>" = { keys, macro, sha256 }`.
- **`state.json`** holds what the app remembers: the window and dialog places, picker folders and other `[workspace]` keys, the recents, the script dialogs' last answers, the usage-data id, the skipped update, the last style catalog and the last script. `toolbar.actions`, `toolbar.alignment` and `program.tabTextMaxChars` are choices, so they stay in `settings.toml`.
- **Editing by hand.** Edit the files while HikariSub is closed, because it writes them from memory and keeps no comments. It does keep keys it doesn't know.
- **A file that doesn't read is never overwritten.** That covers a TOML or JSON error, and a `version` that is missing or newer than 1. The file is renamed `<name>.broken` (or `.broken-2` and on), its settings take their defaults, and a notice names the file, line and column. Fix it while HikariSub is closed and give it its name back.
- **`hikari.ini` before them.** The first start without `settings.toml` converts `hikari.ini` into the three files once and renames it `hikari.ini.old`, which is never written again. Import legacy settings still reads legacy's `Config.txt` and `Hotkeys.txt`, and writes into these files.

**List files (CF2, #489).** The lists you build up are TOML files too, each starting with `version = 1` and then one array of tables with named fields:
- **`rules.toml`** holds the Fix minor errors rules: `[[rule]]` with `description`, `find`, `replace`, `enabled` and the options `matchCase`, `lowerCase`, `upperCase`, `keepCase`, `onlyInTags` and `onlyInText` (written when true). A file with no rules is an empty list; without the file the shipped rules are used.
- **`shapes.toml`** holds the drawing tool's shapes: `[[shape]]` with `name`, `drawing`, `fromCursor` (`"widthAndHeight"`, `"keepAspectRatio"` or `"widthOnly"`) and `scaling` (`"points"` or `"scale"`).
- **`tags.toml`** holds the all-tags tool's tags: `[[tag]]` with `name`, `tag`, `min`, `max`, `step`, `decimals`, `values` (1 to 4 numbers), `placing` (`"cursor"`, `"textStart"` or `"clipAnimation"`) and `change` (`"add"`, `"set"`, `"multiply"`, `"multiplyAdd"`, `"gradientCharsUp"`, `"gradientCharsDown"`, `"gradientLinesUp"` or `"gradientLinesDown"`).
- **`catalogs/fonts.toml`** holds the font catalogs: `[[catalog]]` with `name` and `fonts`. The catalog window's safety copies are `catalogs/fonts.autosave-0.toml` to `-2`, and its Load reads a `fonts.toml` or legacy's `FontCatalogs.txt`.
- **The legacy files before them.** Each start converts `Rules.txt`, `ShapesSettings.txt`, `AllTagsSettings.txt`, `catalogs/FontCatalogs.txt` and `catalogs/FontCatalogsAutosave0.txt` to `2.txt` into these files once, when the TOML file is missing, and renames the old file `<name>.old`, which is never written again. The Log says so. A legacy file that can't be read is left as it is, its list takes its defaults and isn't written, and the next start tries again. Import legacy settings still reads legacy's `Config/Rules.txt`, and writes `rules.toml`.
- They're written as the settings files are: edit them while HikariSub is closed, keys HikariSub doesn't know are kept, and a file that doesn't read becomes `<name>.broken` while its list takes its defaults. Two HikariSubs on one folder take turns writing, and the last list written wins. The style catalogs (`catalogs/*.sty`) and `dictionaries/UserDic.udic` keep their own formats.

**Bundled files.** Each package ships `bundled-files.txt` beside the program: the SHA-256 of every file under `Automation/automation` and of the `Dictionary` folder's own `.dic` and `.aff` files (`cmake/HikariBundledManifest.cmake`). Each start copies them into the user folder (`automation/Autoload` and `Include` into `automation/autoload` and `include`, the dictionaries into `dictionaries`): a missing file is copied in; a file still as the bundled version it came from is replaced by the new one; a file changed since (by the user, or by a DependencyControl update) is kept, and the Log says so; a file a new version no longer brings is removed unless it was changed. `.bundled-files` in the user folder records which bundled version each file came from ([UD1-seeded-bundle](compatibility-decisions.md)). Autoload scripts load from the shipped `automation/Autoload`, then from the user folder's `automation/Autoload` and `automation/autoload`, where a script replaces a shipped one of the same name; scripts search the user folder's `automation/Include` and `include` before the shipped `Include`. `?user`, `?local` and `?temp` resolve into the user folder, `?data` into the shipped `Automation` folder.

**Earlier Qt folders.** The first start of a version with the user folder moves the Qt folders before it into it once, the first time it has no settings (`settings.toml`, `hikari.ini` or `hikari.ini.old`; recorded in `.old-folders` in the user folder, so deleting them later brings nothing back): `~/.config/HikariSub/HikariSub` and `~/.local/share/HikariSub/HikariSub` on Linux, `%LOCALAPPDATA%\HikariSub\HikariSub` and `%APPDATA%\HikariSub\HikariSub` on Windows. Their contents go into the layout (`hikari.ini` to the top, where it is converted as above; `Dictionary` to `dictionaries`, `Catalog` and `FontCatalogs*.txt` to `catalogs`, `layouts.json` to `presets`, `Recovery` to `recovery`, the `Automation` folder's contents to the top, its `automation/Autoload` and `Include` to `automation/autoload` and `include`), caches to the cache folder; what the user folder already has stays where it was, and so does the old DependencyControl (the bundled release replaces it); on Windows, where the old data folder is inside the user folder, what stays of it is in `%APPDATA%\HikariSub\old-HikariSub`. A notice names the folder. Legacy's folders (`%LOCALAPPDATA%\HikariSub\Legacy`, `~/.local/share/HikariSub/Legacy`, a portable legacy copy's own) are never touched, so Import legacy settings keeps working. A portable copy and a start with `HIKARISUB_USER_DIR` move nothing; a portable copy's first start names the old folder when it holds an earlier version's `hikari.ini` ([UD1-move-in](compatibility-decisions.md), [BUG397-move-in](compatibility-decisions.md)).

**Sessions.** The last session is `last-session.json` in the user folder, and Save session writes `.hksession` files. Both are JSON: `version`, then `tabs`, each with its subtitles, video and position, audio, keyframes, active Line, scroll and panel layout, and the active tab marked. Paths are absolute. Load session also opens HikariSub legacy `.kls` files, which the app never writes; opening a `.hksession` or `.kls` from the file manager, or dropping one on the window, loads it the same way. The first start of a version with `last-session.json` converts `LastSession.txt` into it and keeps the old file as `LastSession.txt.old`. A `last-session.json` that cannot be read is kept as `last-session.json.broken` with a notice naming the file and line, and no tabs are restored; a folder in its place, or a file HikariSub may not open, stays where it is and is not written over. A `LastSession.txt` HikariSub may not open waits for a later start. Linux packages register `.hksession` as `application/x-hikarisub-session`.

## Versions and the move from legacy

Legacy stays at 0.0.x and HikariSub starts at 0.1.0; `HIKARI_VERSION_SUFFIX` adds a prerelease (`0.1.0-beta.2`). deb and rpm versions put `~` before the prerelease inside the package (`0.1.0~beta.2-1`), never in the file name. Moving from legacy to HikariSub is an ordinary upgrade of one package (`hikarisub`, or `hikarisub-stable-bin` and `hikarisub-beta-bin` on the AUR, whose `pkgver` is the version without its `-`: `0.1.0-beta.2` is `0.1.0beta.2`, which vercmp sorts above every legacy 0.0.x and below `0.1.0`) or one installation.

A HikariSub release (0.1.0 and up) always names `"offer_to": ["qt"]`. Legacy users are offered it only through its manifest's optional `offer` member, which legacy 0.0.2 and later read and which never downloads anything before the user accepts ([ADR-0021](adr/0021-opt-in-offer-of-the-rewrite-to-legacy.md)). On the AUR, `hikarisub-beta-bin` follows HikariSub from 0.1.0-beta.1, and `hikarisub-stable-bin` follows it from its first stable release (0.1.0). Legacy 0.0.1 reads no manifest and reports the highest stable release, so 0.1.0's release notes open by saying that moving is optional.

## Testing an update

A test build (`-DHIKARI_UPDATE_TEST_FEED=ON`; off in releases, whose CI fails if the binary names `HIKARISUB_UPDATE_FEED`) reads `HIKARISUB_UPDATE_FEED=<base URL>`: `<base>releases.json` for the list, `<base>download/v<V>/<asset>` for the files and `<base>releases/tag/v<V>` for the pages. It also reads `HIKARISUB_PACKAGE_KIND=<token>` in place of the marker (and `HIKARISUB_AUR_CHANNEL` in place of `aur-channel.txt`), so the AUR notice and the other flows can be tried without installing a package. `tools/update-feed/make-feed.py` builds such a feed from a folder of packages.
